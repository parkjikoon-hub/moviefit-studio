윈도우 PowerShell 5.1의 `Get-Content`는 한글 파일을 cp949로 읽어서, **UTF-8 한국어 문장을 찾는 검사가 조용히 실패한다.** 영어는 찾고 한국어만 못 찾으므로, "그 기능이 안 들어갔다"는 잘못된 결론에 이른다.

## 무슨 일이 있었나 (2026-08-13)

설치본에 방금 만든 고침이 들어갔는지 확인하려고 이렇게 했다.

    Get-Content "$dir\app\static\app.js" -Raw) -match '프로그램과 연결이 끊겼습니다'
    → False

그래서 **"프로그램이 켜져 있어서 설치가 조용히 실패했다"** 고 결론 내렸다.
파일 수정 시각도 그대로여서 확신했다. 사용자에게 그렇게 보고했고, 그 근거로
설치 스크립트에 AppMutex 를 넣는 작업까지 했다.

**둘 다 틀린 근거였다.**

    저장소 app/static/app.js   sha256 7816d21fd35e
    설치본 app/static/app.js   sha256 7816d21fd35e   ← 완전히 같다
    파이썬으로 UTF-8 로 읽으니 '프로그램과 연결이 끊겼습니다' 가 **들어 있었다**

### 왜 못 찾았나

윈도우 PowerShell 5.1(`powershell.exe`)의 `Get-Content` 는 BOM이 없으면
**시스템 ANSI 코드페이지(한국 윈도우 = cp949)** 로 읽는다. UTF-8로 저장된 한글은
글자가 깨져서 원문과 일치하지 않는다. 그런데 **영어·숫자는 멀쩡히 읽힌다.**

    $m -match 'MovieFitStudioRunning'      → True   (ASCII 라서 통과)
    $js -match '프로그램과 연결이 끊겼습니다'   → False  (한글이라 실패)

이 조합이 지독하다. 같은 방식으로 검사한 항목 중 **영어는 다 통과하고 한국어만
실패**하므로, "일부 파일만 갱신된 반쪽 설치" 처럼 보인다. 실제로 그렇게 읽고
존재하지 않는 결함을 진단했다.

### 파일 시각도 근거가 아니었다

설치본 `app.js` 의 수정 시각이 이전 설치 때 그대로여서 "덮어쓰지 못했다"고 봤다.
**Inno Setup 은 원본 파일의 시각을 그대로 복사한다.** 저장소 파일을 고치지 않은
회차라면 시각이 안 변하는 것이 정상이다. 시각은 덮어쓰기 여부의 증거가 아니다.

## 앞으로 지킬 것

1. **파일 내용을 검사할 때는 PowerShell 로 읽지 말고 파이썬으로 인코딩을 밝혀 읽는다.**

       pathlib.Path(p).read_text(encoding="utf-8")

   꼭 PowerShell 로 읽어야 하면 `Get-Content -Encoding UTF8` 을 **반드시** 붙인다.

2. **"같은 파일인가"는 글자 검사보다 해시가 낫다.** 인코딩과 무관하고 한 줄이면 된다.

       hashlib.sha256(pathlib.Path(p).read_bytes()).hexdigest()

3. **검사가 False 를 돌려줬을 때, 대상이 아니라 검사를 먼저 의심한다.**
   특히 "영어 항목은 통과하는데 한국어 항목만 실패"하면 그것은 결함의 모양이 아니라
   **인코딩 문제의 모양**이다.

4. **파일 수정 시각을 설치 여부의 증거로 쓰지 않는다.** 설치 도구가 원본 시각을 보존한다.

## 곁들여 확인된 것 (이건 사실이다)

- 설치 스크립트의 `AppMutex` 는 실제로 동작한다. 프로그램을 켜 둔 채 설치를 시도하니
  설치가 **중단**되었고(`EAbort`, 종료 코드 1) **파일을 하나도 건드리지 않았다.**
- 다만 **AppMutex 가 없었다면 정말로 조용히 실패했을지는 시험하지 않았다.**
  그 장치를 넣은 근거는 위 오진이었다. 장치 자체는 표준적이고 해로울 것이 없어
  남겨 두지만, **"이런 결함이 있었다"고 말해서는 안 된다.**
- 설치할 때 `/S` 는 NSIS 용이라 Inno Setup 에는 통하지 않는다. `/VERYSILENT` 를 쓴다.
  기록을 남기려면 `/LOG=경로`, 창을 띄우지 않으려면 `/SUPPRESSMSGBOXES` 를 함께 쓴다.

왜 중요한가: 이 실수는 [[generated-files-need-a-different-kind-of-test]] 가 경고한 것과
정반대 방향이다. 그쪽은 **잘못됐는데 통과하는** 검사였고, 이쪽은 **멀쩡한데 실패하는**
검사다. 후자는 없는 결함을 쫓아 시간을 쓰고, 더 나쁘게는 **없는 결함을 고쳤다고
보고하게** 만든다.
