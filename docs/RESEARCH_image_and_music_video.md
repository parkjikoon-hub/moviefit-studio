## 이 문서를 읽는 법

- **코드는 한 줄도 고치지 않았다.** 이 문서는 "무엇을 어떻게 만들 것인가"를 정하기 위한 조사 결과다.
- 문장 끝의 표시가 신뢰 등급이다.
  - **[확인됨]** — 소스 코드를 직접 읽었거나, 명령을 실제로 실행해서 결과를 눈으로 본 것.
  - **[실측]** — 이번 조사에서 FFmpeg을 실제로 돌려 숫자를 잰 것. 실행 기록이 있다.
  - **[확인 안 함]** — 그럴 것이라고 판단했지만 실행해 보지 않은 것. **믿지 말고 만들기 전에 확인할 것.**
- 전문 용어에는 괄호로 뜻을 붙였다.

## 0. 세 줄 요약

1. **N-4(자막→대본)는 이미 만들어져 있다.** 요청서에는 "미구현"이라고 적혀 있지만, 화면에 단추가 있고 동작한다 [확인됨]. 남은 것은 안내 문구 보강 정도이며 반나절도 걸리지 않는다.
2. **N-2(음원 영상)의 가장 어려워 보였던 부분 — 사용자가 음악을 들으며 [지금!]을 눌러 가사 시각을 찍는 기능 — 도 이미 만들어져 있다** (`두드려 맞추기`, 스페이스바) [확인됨]. 음원 영상은 "새 기능"이라기보다 "이미 있는 부품 세 개를 잇는 일"에 가깝다.
3. **진짜 어려운 것은 사진 여러 장을 영상으로 만드는 부분이며, 그 이유는 예상과 다르다.** 명령이 길어서가 아니라 ① 사진 크기가 제각각이면 FFmpeg이 **오류 없이 틀린 영상**을 만들고 ② 가장 흔히 소개되는 방법(`-loop 1`)이 사진 수십 장에서 **메모리 부족으로 죽기** 때문이다. 둘 다 이번 조사에서 실제로 재현했다 [실측]. 대신 확실히 동작하는 방법도 찾아 120초짜리 영상을 15초 만에 만드는 것까지 확인했다 [실측].

## 1. 지금 프로그램이 "영상 파일 하나"를 얼마나 강하게 전제하고 있는가

결론부터: **전제는 강하지만, 막고 있는 지점은 적고 뚜렷하다.** 아래 표의 자리만 손대면 된다.

### 1.1 확장자 관문 — `MEDIA_EXTS`

`app/config.py` 19~21행 [확인됨]:

```python
VIDEO_EXTS = {".mp4", ".mov", ".mkv", ".webm"}
AUDIO_EXTS = {".mp3", ".wav", ".m4a"}
MEDIA_EXTS = VIDEO_EXTS | AUDIO_EXTS
```

이미지 확장자가 아예 없다. 이 값이 **세 곳**에서 문을 막는다 [확인됨].

| 막는 자리 | 파일·행 | 하는 일 |
|---|---|---|
| ① 프로젝트 만들기 | `app/api/projects.py` 38~40행 | `path.suffix.lower() not in MEDIA_EXTS` 이면 400 오류 "지원하지 않는 형식입니다" |
| ② 파일 선택 창 결과 검사 | `app/api/system.py` 42~45행 | 같은 검사를 한 번 더 한다 |
| ③ 파일 선택 창 자체 | `app/core/filedialog.py` 23행 | 탐색기 창의 "파일 형식" 목록이 `*.mp4 *.mov ... *.m4a` 뿐이라 **사진이 화면에 보이지도 않는다** |

③ 이 특히 중요하다. ①②만 고치면 사용자는 "모든 파일"을 골라야 사진이 보이는 이상한 상태가 된다.

그리고 `filedialog.py` 34행은 `askopenfilename`(파일 **한 개**)을 쓴다 [확인됨]. 사진 수십 장을 고르려면 `askopenfilenames`(파일 **여러 개**, 끝에 s가 붙는다)로 바꿔야 한다. 이 함수는 파일 목록을 튜플로 돌려주므로 반환값 처리도 함께 바뀐다.

### 1.2 프로젝트 구조 — `project.json`

`app/core/projects.py`의 `default_project()` 52~81행 [확인됨]. 핵심만 옮기면:

```python
"video_path": video_path,   # 문자열 하나 또는 None
"mode": mode,               # "video" 또는 "script"
"script": "",
"segments": [],
"style": {...},
"output": {...},            # 화면비 (aspect/fit/focus_x/focus_y/pad_blur)
"narration": {...},
```

- 그림의 출처는 **문자열 딱 하나(`video_path`)** 다. 목록이 아니다.
- 각 장의 표시 시간을 적을 곳이 없다.
- 음원을 따로 둘 자리가 없다 (mp3를 넣으면 `video_path` 자리에 들어간다).
- `mode`는 "영상 모드 / 대본 모드" 두 값뿐이며, 이건 **왼쪽 패널을 무엇으로 바꿀지**를 정하는 값이다 (`app/static/app.js` 293~301행) [확인됨]. 여기에 세 번째 값을 넣으면 두 단추짜리 토글이 깨진다.

### 1.4 mp3만 든 프로젝트는 지금 어디까지 되고 어디서 깨지는가 [확인됨 + 실측]

`MEDIA_EXTS` 에 mp3가 이미 있으므로 **mp3로 프로젝트를 만드는 것 자체는 지금도 된다.** 그래서 "음원 영상"은 완전한 백지가 아니다. 실제로 되는 것과 깨지는 것을 갈라 보면:

| 기능 | mp3 프로젝트에서 | 근거 |
|---|---|---|
| 프로젝트 만들기 | **된다** | `MEDIA_EXTS` 에 `.mp3` 포함 [확인됨] |
| 음성인식으로 자막 만들기 | **된다** | `stt.transcribe()` 는 파일 종류를 가리지 않는다 [확인됨] |
| 재생·시간 흐름·탭 싱크 | **된다** | 브라우저의 `<video>` 태그는 mp3도 재생한다. 다만 `app.js` 257행이 `player.hidden = false` 를 조건부로만 하므로 실제로는 보이지 않게 처리된다 [확인됨] |
| 파형(타임라인 배경) | **된다** | `audio_analysis` 는 소리만 본다 [확인됨] |
| 화면비 틀 그리기 | **안 된다** | `videoWidth`가 0 → `sourceDimensions()` 가 null [확인됨] |
| 자막 번인 (영상 만들기) | **안 된다** | `video_dimensions()` 가 ffprobe로 영상 트랙을 찾는데 mp3에는 없다. 실측: `ffprobe -select_streams v:0` 결과가 빈 목록 → `IndexError` → `RenderError("영상에서 화면 크기 정보를 찾지 못했습니다.")` [실측] |

즉 **음원 영상에서 새로 만들어야 하는 것은 "그림"뿐이다.** 시간·자막·소리 쪽은 이미 굴러간다.

## 2. FFmpeg 실측 — 사진 여러 장을 영상으로 만드는 방법

이 절의 모든 숫자는 이번 조사에서 실제로 명령을 돌려 얻은 것이다. 실행 환경: FFmpeg 8.1 (gyan.dev full build, libass·xfade·zoompan 포함) [확인됨].

### 2.1 방법 ㉮ — concat 데먹서 (이어붙이기 목록) : **그냥 쓰면 조용히 틀린다**

`concat` 데먹서는 아래처럼 목록 파일을 주면 파일들을 차례로 이어 준다. 장당 표시 시간(`duration`)도 적을 수 있다.

```
file 'a.jpg'
duration 3
file 'b.jpg'
duration 2
```

**실측 1 — jpg와 png를 섞으면 오류가 난다.**
목록에 jpg 2장 + png 1장을 넣자 이렇게 나왔다:

```
[mjpeg @ ...] No JPEG data found in image
[vist#0:0/mjpeg @ ...] Error submitting packet to decoder: Invalid data found
```

이유: concat 데먹서는 목록 **전체에 대해 해독기(디코더)를 하나만** 고른다. 첫 파일이 jpg라 mjpeg 해독기를 골랐고, png를 그 해독기에 넣으니 실패했다. 그런데 **FFmpeg의 종료 코드는 0(성공)이었다** — 실패한 장면만 빠진 영상이 만들어진다.

**실측 2 — 전부 jpg여도 크기가 다르면 결과가 통째로 틀린다. 오류 메시지는 없다.**

- 넣은 것: 1920×1080(빨강) 3초 → 800×1200(초록) 2초 → 640×480(파랑) 4초. 기대 길이 9초.
- 나온 것: 길이 **8.0초**. 그리고 t=1초·4초·7초에서 화면 가운데 색을 재 보니 **셋 다 파랑(0,0,254)** 이었다. 빨강과 초록은 영상에 **한 프레임도 들어가지 않았다.**
- 종료 코드 0, 경고 문구 없음.

> **이것이 이 기능에서 가장 위험한 함정이다.** 개발자가 같은 크기의 시험용 사진 3장으로 만들어 보면 멀쩡히 통과하고, 사용자가 휴대폰 사진(가로·세로 섞임)을 40장 넣는 순간 "마지막 사진만 2분 동안 나오는 영상"이 나온다. 오류가 안 나므로 원인을 찾기도 어렵다.

### 2.2 방법 ㉯ — `-loop 1` 로 사진마다 입력을 열고 `concat` **필터**로 잇기 : **몇 장은 되지만 수십 장에서 죽는다**

```
ffmpeg -loop 1 -t 3 -i a.jpg  -loop 1 -t 2 -i b.png  -loop 1 -t 4 -i c.jpg \
  -filter_complex "[0:v]scale=...,pad=...[v0]; [1:v]...[v1]; [2:v]...[v2]; [v0][v1][v2]concat=n=3:v=1:a=0[vout]" ...
```

**실측 3 — 3장에서는 완벽하다.** jpg·png를 섞고 크기를 제각각으로 해도 길이 정확히 9.000초, t=1/4/7초의 색이 각각 빨강(254,0,0)·초록(0,127,0)·파랑(0,0,254)으로 **의도한 그대로** 나왔다. 사진마다 따로 `scale`·`pad`를 걸 수 있는 것이 이 방법의 장점이다.

**실측 4 — 60장에서는 죽는다.**

```
[mjpeg @ ...] get_buffer() failed
[dec:mjpeg @ ...] Error submitting packet to decoder: Cannot allocate memory
[fc#0 @ ...] Task finished with error code: -12 (Cannot allocate memory)
```

- 필터그래프를 파일로 빼는 `-filter_complex_script` 로 바꿔도 **똑같이 죽었다.**
- 즉 **명령줄 길이 문제가 아니다.** 실제로 잰 길이는 전체 18,950자였고, 윈도우의 한계(32,767자)에 한참 못 미친다 [실측]. 60장 기준 입력 인자 11,329자 + 필터그래프 7,495자.
- 진짜 원인은 **메모리**다. `-loop 1` 은 사진 한 장을 무한히 되풀이하는 입력이라 FFmpeg이 60개 입력을 동시에 열고 각각 앞질러 버퍼를 채운다. 1080×1920 프레임 하나가 약 3MB이고 이게 입력마다 여러 장씩 쌓인다.
- 참고로 명령줄 길이만 따져도 대략 **100장 근처에서 윈도우 한계에 닿는다** (60장에 18,950자였으므로 장당 약 316자) [실측에 근거한 산술].

### 2.3 방법 ㉰ — **먼저 크기를 맞춰 두고, 그다음 concat 데먹서** : **채택 권고**

두 단계로 나눈다.

1. **정규화** — 사진 한 장씩 작은 FFmpeg 명령을 돌려 **똑같은 크기의 jpg**로 다시 저장한다. 이때 crop/pad(잘라내기/여백 채우기)를 적용한다.
2. **이어붙이기** — 크기가 전부 같아졌으므로 concat 데먹서가 정상 동작한다. 목록은 **파일**이므로 명령줄 길이 문제가 원천적으로 없다.

**실측 5 — 60장, 장당 2초, 1080×1920 세로 영상**

| 단계 | 걸린 시간 |
|---|---|
| 사진 60장 정규화 (각각 1회 ffmpeg 호출) | **3.8초** |
| 이어붙이며 h.264로 인코딩 | **11.2초** |
| **합계** | **약 15초** (결과 영상 길이 120초) |

**실측 6 — 사진이 바뀌는 시각이 정확한가 (자막과 맞춰야 하므로 중요)**
60장 중 1·2·3·30·59·60번째 사진에 대해, 각 사진의 시작 직후(+0.05초)와 끝 직전(−0.05초)에서 화면 색을 재어 그 사진의 색과 대조했다. **12개 표본 전부 일치** (jpeg 압축 오차 ±2 이내). 어긋난 표본 0개.

**실측 7 — 알아 둘 꼬리 하나.** concat 목록의 마지막 항목 처리 때문에 결과가 **의도보다 2초 길게** 나왔다 (기대 120.0초 / 실제 122.0초). 마지막 줄을 되풀이해 적는 관행 때문이다. `-t` 로 전체 길이를 못 박거나 목록 만드는 규칙을 다듬으면 해결된다 — 만들 때 **반드시 길이를 ffprobe로 재서 확인할 것.**

**실측 8 — webp도 된다.** 900×700 webp를 정규화 단계에 넣으니 1080×1920 jpg로 잘 나왔다. 정규화가 형식 차이까지 흡수해 주므로 **jpg·png·webp 섞임 문제가 이 방법에서는 아예 사라진다.**

### 2.4 사진 + 음원 + 가사 자막을 **한 번에** 만들 수 있는가 [실측]

된다. 실제로 돌려 본 명령의 뼈대:

```
ffmpeg -y -f concat -safe 0 -i 목록.txt \
       -i 노래.mp3 \
       -vf "fps=30,ass=가사.ass,format=yuv420p" \
       -map 0:v -map 1:a \
       -c:v libx264 -crf 20 -c:a aac -b:a 192k -shortest -movflags +faststart 결과.mp4
```

- 결과: 길이 **정확히 10.000초** (음원 길이와 같음), 1080×1920, 영상·소리 트랙 둘 다 있음. 1.2초 만에 완성.
- `-shortest` 가 "음원이 끝나면 영상도 끝"을 보장한다.
- 자막(`ass=`)은 **상대 경로**로 넣었고 정상 동작했다 — 즉 `app/core/ffmpeg.py`의 `_filter_paths()` 방식(작업 폴더를 자막 파일 폴더로 잡고 파일 이름만 넘기기)을 **그대로 재사용할 수 있다.** `memory/ffmpeg-filter-path-escaping.md` 의 함정을 다시 밟지 않는다.

### 2.5 전환 효과(사진이 스르륵 바뀌는 것)는? [확인 안 함]

`xfade` 필터가 이 FFmpeg 빌드에 있다는 것만 확인했다 [확인됨]. 그러나 **xfade는 방법 ㉯ 계열이라 입력을 동시에 여러 개 열어야 하고, 사진 N장을 이으려면 필터를 N−1번 사슬로 엮어야 한다.** 2.2의 메모리 문제가 그대로 따라올 가능성이 높다 [확인 안 함]. 지금 단계에서는 **전환 효과 없이(딱딱 바뀜) 먼저 만들고**, 나중에 필요하면 "정규화된 사진들로 짧은 mp4 조각을 각각 만들어 두고 조각끼리 xfade" 같은 별도 방법을 따로 조사할 것을 권한다.

## 3. 화면(미리보기)이 깨지는 지점

### 3.1 `<video>` 태그 — 사진 프로젝트에는 재생할 것이 없다

`app/static/app.js` 255~271행 [확인됨]:

```js
if (project.video_path) {
  player.src = `/media/project/${...}/video`;
  player.hidden = false; player.controls = true;
  ...
} else {
  player.removeAttribute("src"); player.hidden = true;   // ← 시계가 멈춘다
  $("#no-video").hidden = false;
  box.classList.add("is-empty");
}
```

`<video>` 가 없으면 `player.currentTime` 이 0에 붙박이가 되고, 그것에 매달린 것이 전부 죽는다: 타임라인의 재생 위치 표시, 자막 오버레이 갱신, **두드려 맞추기(탭 싱크)**, A-B 구간 반복.

**대응 (권고)**: `<video>` 를 **시계와 소리 담당**으로 남긴다.
- 음원 영상이면 `player.src` 에 **mp3 주소**를 넣는다. 브라우저의 `<video>` 태그는 오디오 파일을 문제없이 재생하며 `currentTime`·`duration`·`play()`·`timeupdate` 가 전부 평소처럼 동작한다 [확인 안 함 — 표준 동작이지만 이 화면에서 실제로 눌러 확인할 것].
- 소리가 없는 사진 영상이면 재생할 파일 자체가 없으므로, `<video>` 대신 **자바스크립트 타이머로 도는 가짜 시계**가 필요하다. 이때 `currentTime`을 읽는 곳이 여러 군데이므로, **"지금 시각을 돌려주는 함수 하나"를 만들어 모든 곳이 그것을 거치게** 해야 한다. 지금은 `$("#player").currentTime` 을 최소 12곳에서 직접 읽는다 [확인됨].
- 그림은 `<video>` 아래에 **`<img>` 층**을 하나 깔고, 시각이 바뀔 때마다 그 시각에 해당하는 사진으로 갈아 끼운다.

### 3.2 화면비 계산 — `framing.py` 는 **고칠 필요가 없다. 다만 쓰는 방식이 달라진다**

`app/core/framing.py` 의 `resolve(src_width, src_height, output)` 는 "**원본 하나**를 목표 화면비에 맞게 어떻게 자르거나 채울지"를 계산한다 [확인됨].

사진 영상에는 "원본 하나"가 없다. 그래서 관계가 뒤집힌다.

- **영상 프로젝트**: 원본 크기가 정해져 있고 → 화면비를 고르면 → 출력 크기가 **계산되어** 나온다.
- **사진 프로젝트**: 원본이 여러 개라 기준이 없고 → 화면비를 고르면 그것이 **곧 출력 크기(캔버스)** 다. 사진들이 거기에 맞춰 들어간다.

권고하는 처리:

1. 사진 프로젝트는 캔버스 크기를 프로젝트에 **직접 저장한다** (예: 9:16 → 1080×1920, 16:9 → 1920×1080, 1:1 → 1080×1080).
2. `framing.resolve(캔버스가로, 캔버스세로, output)` 을 그대로 부른다. 캔버스 자체가 이미 그 화면비이므로 `changed=False`, `filter=None` 이 나오고 [코드상 116~150행 논리로 그렇게 된다 — 확인됨], `width/height` 는 캔버스 크기가 된다. **즉 자막(ASS) 만들기와 화면 오버레이는 지금 코드 그대로 맞아떨어진다.**
3. "원본 그대로(`source`)" 선택지는 사진 프로젝트에서 뜻이 없다. 화면에서 감추거나 16:9로 기본 지정할 것.

**그런데 `framing.resolve()` 를 사진 한 장씩 맞추는 데 쓸 수는 없다.** 이유가 두 가지다 [확인됨, 코드 근거]:
- `crop` 갈래(127~150행)는 잘라낸 **그 크기**를 출력으로 삼는다. 사진마다 크기가 달라서 결과 크기도 제각각이 된다 → 2.1의 조용한 실패로 직행한다.
- `pad` 갈래(158~164행)는 틀 크기를 **"원본의 긴 변"** 으로 정한다. 사진마다 긴 변이 다르니 역시 결과 크기가 제각각이 된다.

**권고**: `framing.py` 안에 형제 함수를 하나 더 만든다. 이름 예: `fit_filter(img_w, img_h, canvas_w, canvas_h, fit, focus_x, focus_y, pad_blur) -> str`. 하는 일은 "이 사진을 **반드시 정확히** canvas_w×canvas_h 로 만드는 필터 문자열을 돌려준다"이다. crop·pad·흐린 배경(`gblur`)이라는 **말과 개념은 지금과 똑같이 쓴다.** 새 파일이 아니라 `framing.py` 안에 두는 이유는, 이 프로젝트가 "잘라내기·여백 채우기 규칙은 한 파일에만 있다"를 이미 지켜 왔고 그것을 깨면 다음 사람이 두 곳을 따로 고치게 되기 때문이다 (`memory/design-change-has-copies-elsewhere.md` 의 교훈).

필요한 필터 자체는 2.3에서 실제로 돌려 확인했다 [실측]:
- 여백 채우기: `scale=W:H:force_original_aspect_ratio=decrease,pad=W:H:(ow-iw)/2:(oh-ih)/2:black,setsar=1`
- 잘라내기: `scale=W:H:force_original_aspect_ratio=increase,crop=W:H:<x>:<y>,setsar=1`
- 흐린 배경: `framing.py` 176~182행의 `split/gblur/overlay` 조합을 그대로 쓰면 된다 [확인 안 함 — 사진 입력으로는 돌려보지 않았다]

`setsar=1`(화소 모양비를 1:1로 못박음)을 빠뜨리면 사진에 따라 결과가 찌그러질 수 있다. 실측에서는 넣고 돌렸다.

### 3.3 자막 위치가 결과와 어긋나는 문제가 **되살아난다** — 가장 조심할 곳

`memory/preview-must-use-the-output-frame.md` 에 기록된 결함이 사진·음원 프로젝트에서 그대로 재발한다.

`app/static/app.js` 2333~2337행 [확인됨]:
```js
function sourceDimensions() {
  const p = $("#player");
  if (!p || !p.videoWidth || !p.videoHeight) return null;   // ← 사진·음원 프로젝트는 언제나 여기
  return { w: p.videoWidth, h: p.videoHeight };
}
```

그리고 906~909행 [확인됨]:
```js
function outputFrameRect() {
  const dims = sourceDimensions();
  const conf = currentOutput();
  if (!dims || conf.aspect === "source") return { left: 0, top: 0, w: 1, h: 1 };   // ← 통째로 무력화
  ...
}
```

`sourceDimensions()` 가 null이면 `outputFrameRect()` 가 "상자 전체"를 돌려주고, 그러면 **자막을 그리는 자리와 마우스로 끄는 자리와 실제로 새겨지는 자리가 서로 달라진다.** 메모리 문서의 실측에 따르면 이 어긋남이 438픽셀까지 벌어졌다.

**대응**: `sourceDimensions()` 가 `videoWidth`가 없을 때 **프로젝트에 저장된 캔버스 크기**를 돌려주게 한다. 한 줄짜리 수정이지만 이걸 빼먹으면 "화면에서는 잘 보이는데 저장하면 자막이 없는" 상태가 된다. 그리고 메모리 문서의 경고대로 **그리는 쪽과 끄는 쪽을 반드시 짝으로** 확인해야 한다.

### 3.4 자막 번인 — 사진에는 그대로 되고 mp3에는 안 된다

`app/core/ffmpeg.py` 의 `video_dimensions()` 를 사진과 mp3에 각각 돌려 봤다 [실측]:

| 입력 | `ffprobe -select_streams v:0 stream=width,height` 결과 |
|---|---|
| `a.jpg` (1920×1080) | `{"streams":[{"width":1920,"height":1080}]}` → **정상 동작** |
| `song.mp3` | `{"streams":[]}` → `IndexError` → `RenderError("영상에서 화면 크기 정보를 찾지 못했습니다.")` |

즉 **사진 한 장을 `video_path` 에 넣으면 지금 코드로도 크기 측정이 된다.** 다만 `burn_subtitles()` 는 입력을 한 개로 전제하고 `-i 원본` 하나만 넣으므로, 사진 여러 장을 잇는 새 함수가 필요하다.

#### 데이터 모델 제안

```json
{
  "video_path": null,
  "audio_path": "C:/음악/노래.mp3",
  "canvas": { "width": 1080, "height": 1920 },
  "images": [
    { "id": "i001", "path": "C:/사진/01.jpg", "duration": 3.0, "seg_id": null },
    { "id": "i002", "path": "C:/사진/02.png", "duration": 3.0, "seg_id": "s004" }
  ]
}
```

- `images` 가 비어 있지 않으면 사진 영상 프로젝트다. **새 enum(모드 값)을 만들지 않는다** — `mode` 는 지금대로 왼쪽 패널 전환에만 쓴다.
- `seg_id` 가 **N-2의 핵심 한 칸**이다. 값이 없으면 "이 사진은 `duration` 초 동안 보인다", 값이 있으면 "이 사진은 그 자막(가사)이 시작할 때 나타나 다음 사진이 나올 때까지 보인다". **한 구조로 두 기능을 다 덮는다.**
- 옛 프로젝트에는 이 키들이 없다. 읽을 때 `data.get("images") or []` 로 받으면 그대로 열린다 (`output` 키를 나중에 넣었을 때 쓴 것과 같은 방식) [확인됨].

#### 가장 큰 장애물 세 가지

1. **크기 정규화를 빠뜨리면 오류 없이 틀린 영상이 나온다** (2.1 실측). → 정규화를 **선택이 아니라 필수 단계**로 만들고, 완성 후 길이·프레임 색을 재는 자동 점검을 함께 짤 것.
2. **`-loop 1` 방식은 수십 장에서 메모리 부족으로 죽는다** (2.2 실측). → 처음부터 방법 ㉰(정규화 후 concat)로 갈 것. 시험은 반드시 **30장 이상**으로.
3. **정규화된 임시 사진의 용량과 정리.** 60장이면 1080×1920 jpg 60개가 프로젝트 폴더에 쌓인다 (실측에서 장당 수십~수백 KB). 원본 사진을 바꾸지 않았으면 다시 만들지 않도록 캐시하고, 어디에 두고 언제 지울지 정해야 한다 [확인 안 함 — 실사용 사진 크기로 용량을 재 보지 않았다].

#### 어려움·소요

**난이도 중상 / 2.5일.** 어려움의 대부분은 FFmpeg이 아니라 **화면**(사진 줄 세우기 UI, `<img>` 층, 시계)에 있다.

### N-2. mp3 + 사진 + 가사 → 음원 영상

사용자가 정한 두 가지 전제:
- 사진은 **가사 자막이 바뀔 때 함께 넘어간다** (가사 줄 ↔ 사진 짝짓기)
- 가사 시각은 **사용자가 들으면서 [지금!]을 눌러 손수 찍는다**

#### 이미 있는 것 — 예상보다 훨씬 많다 [확인됨]

| 요구 | 이미 있는 부품 | 위치 |
|---|---|---|
| 들으면서 [지금!] 눌러 시각 찍기 | **`두드려 맞추기`** — 켜면 스페이스바가 "이 문장 시작"이 되고, 찍을 때마다 다음 자막으로 자동 이동하며 앞 자막의 끝을 이번 시작까지 늘린다 | `app/static/app.js` `toggleTapSync()` 2161~2179행, `tapMark()` 2181~2207행, 단축키 연결 1615행 |
| 가사 여러 줄 → 자막 여러 개 | 대본 붙여넣기 + 문장 나누기 | `splitSentences()`, `app/core/narration.py` `split_script()` |
| 되돌리기 | 찍기 전에 `snapshot()` 을 부름 (2189행) | 이미 들어 있음 |
| 소리 파형 보며 찍기 | 타임라인 배경 파형 | `app/api/audio.py`, `app/core/audio_analysis.py` |
| 구간 반복 들으며 다듬기 | A-B 구간 반복 | `app/static/app.js` `toggleAB()` 2210행~ |
| mp3로 프로젝트 만들기 | `MEDIA_EXTS` 에 이미 포함 | `app/config.py` 20행 |

즉 **N-2에서 진짜 새로 만드는 것은 "그림"과 "짝짓기"뿐이다.**

#### 새로 만들 것

1. **`seg_id` 짝짓기** — N-1의 데이터 모델에 이미 자리를 잡아 두었다. 화면에서는 자막 편집기 각 줄 옆에 사진 미리보기(썸네일)를 놓고, 사진 목록에서 끌어다 놓거나 [이 줄에 넣기]를 누르게 한다.
2. **`seg_id` → `duration` 으로 바꾸는 계산 한 줄** — 렌더링 직전에 "이 사진의 표시 시간 = 다음 사진이 짝지어진 자막의 시작 − 이 사진이 짝지어진 자막의 시작"으로 계산한다. 이렇게 하면 **렌더링 쪽(`slideshow.py`)은 `seg_id` 를 몰라도 되고 N-1과 완전히 같은 코드가 된다.** 이것이 "일반 영상에도 같은 부품이 쓰이게 하라"는 사용자 요구를 만족시키는 지점이다.
3. **첫 사진 앞 / 마지막 사진 뒤 처리** — 첫 가사가 3초에 시작하면 0~3초에 무엇을 보일지 정해야 한다. 권고: 첫 사진을 0초부터 보이게 한다(가장 덜 놀랍다).
4. **길이 맞추기** — `-shortest` 로 음원 길이에 맞춘다 [실측으로 정확히 10.000초 확인]. 사진이 모자라면 마지막 사진을 늘리고, 남으면 잘린다. 어느 쪽인지 **내보내기 전에 알려 줄 것** (`exportWarning` 구조가 이미 있다 — `app.js` 21행 [확인됨]).

#### 가장 큰 장애물

1. **`<video>` 를 mp3 재생기로 쓰는 전환** (3.1). 지금 코드는 `video_path` 가 있으면 무조건 화면에 영상을 보이려 든다. mp3일 때는 "소리는 `<video>`, 그림은 `<img>`" 로 갈라야 한다.
2. **탭 싱크가 mp3에서도 도는지 실제로 눌러 확인.** 코드상 `$("#player").currentTime` 만 쓰므로 될 것으로 보이지만, 지금 `player.hidden = true` 인 경로를 타므로 **눌러 봐야 안다** [확인 안 함]. `memory/verify-ui-by-actually-clicking.md` 의 교훈이 그대로 적용된다.
3. **가사 자막의 줄바꿈 규칙.** 가사는 한 줄 20자 규칙(`max_chars`)에 잘 맞지 않는다. 노래 가사는 "한 줄을 통째로 한 화면에" 보여야 하는데 지금 규칙은 자동으로 쪼갠다. 스타일 패널에 `max_chars` 조절이 이미 있으므로 [확인됨] 값을 크게 잡으면 되지만, **음원 프로젝트의 기본값을 다르게 줄 것**을 권한다.

#### 어려움·소요

**난이도 중 / 1.5일** (N-1이 끝난 뒤 기준). N-1을 하지 않고 이것만 하는 것은 불가능하다 — 사진 파이프라인 전부를 공유한다.

### N-3. 자막 강제정렬 (영상 + 내 대본 → 시간 자동 부여)

#### 지금 코드에서 얻을 수 있는 것

`app/core/stt.py` 의 `transcribe()` 는 `word_timestamps=True` 로 **단어 하나하나의 시각을 이미 받고 있다** (144~149행) [확인됨]. 그런데 162~174행에서 그 `words` 목록을 지역 변수로만 쓰고, `split_into_segments()` 로 자막을 만든 뒤 **단어 목록은 버린다** [확인됨].

```python
words: list[dict[str, Any]] = []
for segment in segment_iter:
    for word in segment.words or []:
        words.append({"word": word.word, "start": ..., "end": ...})
    ...
segments = subtitles.split_into_segments(words, ...)
return {"segments": segments, ...}      # ← words 가 없다
```

**따라서 첫 걸음은 아주 작다: 돌려주는 값에 `words` 를 함께 넣는 것.** 인식을 두 번 돌릴 필요가 없다.

#### 설계 제안

```
사용자 대본 ──┐
              ├─→ 글자 단위로 대조(difflib) ─→ 대본의 각 어절에 시각을 붙임
음성인식 단어 ─┘                                         │
                                                         ▼
                              subtitles.split_into_segments(그 어절 목록)
                                          ↑ 기존 함수를 그대로 씀
```

핵심은 **"대본 어절 + 시각" 목록을 만들어 내면 그다음은 기존 코드가 전부 처리한다**는 것이다. `split_into_segments()` 는 `[{"word":..., "start":..., "end":...}]` 모양만 받으면 되고 (177~181행 문서화됨) [확인됨], 문장 나누기·글자수 제한·사용자 사전까지 이미 그 뒤에 붙어 있다.

대조 방법:
1. 양쪽에서 공백·문장부호를 떼어 낸 **글자 열** 두 개를 만들고, 원래 위치를 기억해 둔다.
2. 파이썬 표준 라이브러리 `difflib.SequenceMatcher` 로 같은 부분을 찾는다. **새 패키지 설치가 필요 없다** — 파이썬에 기본 포함 [확인됨].
3. 대본 어절의 첫 글자가 인식 단어 어느 것에 붙었는지 보고, 그 단어의 `start` 를 대본 어절의 시각으로 삼는다.
4. 짝을 못 찾은 구간(인식이 통째로 놓친 부분)은 **앞뒤로 짝이 맞은 지점 사이를 글자 수 비례로 나눠 채운다.**

#### 가장 큰 장애물

1. **숫자와 영어.** 대본에 "2024년"이라 쓰고 음성인식은 "이천이십사 년"이라 적는다. 글자 대조로는 짝이 맞지 않는다. 대본에 "AI"라 쓰고 인식이 "에이아이"라 적는 경우도 같다. → 이 구간은 4번(비례 배분)으로 떨어지므로 **영상이 깨지지는 않지만 그 부분 시각이 부정확해진다.**
2. **정확도를 사용자에게 정직하게 보여 주는 일.** 위 문제 때문에 "완전 자동"이라고 말하면 안 된다. → **줄마다 "잘 맞음 / 짐작함"을 표시**하고, 짐작한 줄만 사용자가 두드려 맞추기와 ±0.1초 넛지로 다듬게 한다. 두 도구 다 이미 있다 [확인됨].
3. **정확도를 아직 하나도 재 보지 않았다** [확인 안 함]. 이 기능만은 **만들기 전에 `tests/sample/` 의 실제 음성으로 먼저 실험해 볼 것**을 강하게 권한다. 반나절이면 "이 방법이 쓸 만한가"를 알 수 있다.

#### 어려움·소요

**난이도 중 / 1.5일** (그중 0.5일은 정확도 실험). 화면 작업이 거의 없고(대본 붙여넣는 칸 + [시간 붙이기] 단추) 순수 계산이라, N-1보다 위험이 적다. **다만 결과 품질은 완전히 미지수다.**

### N-4. 자막 → 대본 전환 (F-44)

#### **이미 구현되어 있다** [확인됨]

- 화면: `app/static/index.html` 117~121행 — `자막을 대본으로` 묶음, `[자막 텍스트를 대본으로 옮기기]` 단추(`#btn-to-script`), 안내 문구까지 있다.
- 동작: `app/static/app.js` 1489~1495행 —

```js
$("#btn-to-script").addEventListener("click", () => {
  if (!segments().length) { toast("옮길 자막이 없습니다.", { error: true }); return; }
  project.script = segments().map((s) => s.text).filter(Boolean).join("\n");
```

- `docs/ROADMAP.md` 79행에도 Phase 2 수용 기준으로 `[x] 자막을 대본으로 옮기는 버튼이 동작한다 (F-44)` 라고 검증 완료 표시가 있다 [확인됨].

**요청서의 "PRD의 F-44, 미구현"은 사실과 다르다.** 다만 PRD 자체(`docs/PRD.md` 107행)에는 F-44가 P2로만 적혀 있어 상태가 갱신되지 않은 것으로 보인다 — PRD를 손보는 것이 좋겠다.

#### 그래도 남아 있는 진짜 빈틈

사용자의 목적("기존 나레이션 목소리를 바꾸고 싶다")에 비추면 세 가지가 빠져 있다.

1. **원래 자막 시각이 소리 없이 버려진다.** 대본으로 옮긴 뒤 나레이션을 만들면 자막 시각이 **나레이션 길이 기준으로 전부 새로 계산된다** (`narration.recalculate_timings()`) [확인됨]. 즉 공들여 맞춰 놓은 시각이 사라진다. 지금은 아무 경고가 없다.
2. **원본 소리를 어떻게 할지 묻지 않는다.** 목소리를 바꾸려는 사람은 원본 목소리가 **들리면 안 된다.** `original_audio_volume` 기본값은 30(%)이다 [확인됨, `projects.py` 72행]. 목소리 교체 흐름에서는 0이 맞다.
3. **문장 부호가 없는 자막을 그대로 읽힌다.** 자막은 짧게 끊겨 있어 한 줄이 한 문장이 아니다. 그대로 대본으로 쓰면 나레이션이 어색하게 끊긴다. → 옮길 때 "문장부호 기준으로 다시 합칠까요?"를 한 번 물어보면 좋다.

#### 어려움·소요

**난이도 하 / 0.25일.** 안내 대화상자 하나와 기본값 하나.

## 5. 첫 화면(시작 화면)을 어떻게 바꿀 것인가

### 지금 [확인됨]

`app/static/index.html` 17~45행. 진입점은 **둘**이다.

1. 큰 상자 `#drop-zone` — "영상 파일 선택하기 / mp4 · mov · mkv · webm · mp3 · wav · m4a"
2. 아래 작은 단추 `#btn-start-script` — "대본으로 시작하기 (나레이션 만들기)"

(그 밖에 경로 직접 입력 접기 칸과 최근 프로젝트 목록이 있다.)

### 권고 — **진입점 4개, 같은 크기의 카드 한 줄** (추천)

|  | 카드 | 무엇을 고르게 하나 | 어디로 가나 |
|---|---|---|---|
| 1 | **영상으로 시작** | 영상 파일 1개 | 지금과 동일 |
| 2 | **사진으로 시작** | 사진 여러 장 | 사진 패널 + 장당 시간 |
| 3 | **음원으로 시작** | mp3 1개 (사진은 들어가서 추가) | 사진 패널 + 가사 칸 + 두드려 맞추기 |
| 4 | **대본으로 시작** | 아무것도 안 고름 | 지금과 동일 |

**왜 4개인가.** 시작 화면은 사용자가 **자기가 무엇을 가졌는지 확실히 아는** 유일한 지점이다("나는 사진 40장이 있다"). 여기서 숨겨 두면 사용자는 일단 영상 상자를 눌러 보고 사진이 보이지 않아 막힌다. 카드 하나를 더 두는 비용보다 그 막힘의 비용이 크다. `docs/UI_SPEC.md` 의 "메뉴 깊이 최대 2단계, 평평한 UI" 원칙과도 어긋나지 않는다 — 오히려 깊이를 1로 유지하는 방법이다.

**2와 3을 하나로 합치는 안**(사진으로 시작한 뒤 안에서 [음원 넣기])도 검토했다. 카드가 3개로 줄어 깔끔하지만, 음원 영상을 만들려는 사용자가 "사진으로 시작"을 눌러야 한다는 것을 알 방법이 없다. **합치지 않기를 권한다.**

**주의할 점 하나**: 드래그해서 놓기는 지금도 동작하지 않는다. 브라우저가 웹페이지에 파일의 실제 경로를 알려주지 않기 때문이며, 놓으면 안내 문구만 띄운다 (`app.js` 1445~1448행) [확인됨]. 사진 카드에도 같은 제약이 그대로 적용된다. 카드 문구를 "**눌러서** 사진 여러 장 고르기"로 써서 헛기대를 만들지 말 것.

## 6. 단계 나누기 — 각 단계는 따로 완성되고 따로 확인된다

각 단계 끝의 **수용 기준은 "실제로 실행해서 눈으로 볼 수 있는 문장"** 으로 썼다. 이 프로젝트의 규칙대로, 코드를 썼다는 것은 완료가 아니다.

### 단계 1 — 사진이 들어올 통로를 연다 (0.5일)

- `app/config.py` 에 `IMAGE_EXTS` 추가
- `app/core/filedialog.py` 를 여러 파일 선택(`askopenfilenames`)으로 확장 + 사진 필터
- `app/api/system.py`, `app/api/projects.py` 의 확장자 검사에 사진 갈래 추가
- `app/core/projects.py` 의 `default_project()` 에 `images` / `audio_path` / `canvas` 추가

**수용 기준**
1. 시작 화면에서 [사진으로 시작]을 누르면 파일 창에 **jpg·png·webp가 보이고** 여러 장을 한 번에 고를 수 있다.
2. 사진 3장을 고른 뒤 `projects/<프로젝트>/project.json` 을 열면 `images` 에 경로 3개가 순서대로 들어 있다.
3. **`output` 키가 없던 옛 프로젝트가 지금과 똑같이 열린다** (되돌아가기 확인).

### 단계 2 — 사진을 영상으로 만든다 (자막 없이) (1일)

- `app/core/framing.py` 에 `fit_filter()` 추가
- `app/core/slideshow.py` 신규: 정규화 → 목록 파일 → 인코딩, `_run_with_progress()` 로 진행률 보고
- 내보내기 API에 갈래 추가

**수용 기준**
1. **크기가 제각각인 사진 30장(jpg와 png를 섞어서)**, 장당 3초로 내보내면 `ffprobe` 로 잰 길이가 **90.0초 ± 0.1초**, 크기가 정확히 **1080×1920** 이다.
2. t=1초 · 46초 · 89초의 화면을 뽑아 각각 **1번째 · 16번째 · 30번째 사진**과 같은 그림임을 눈으로 확인한다. (2.1의 조용한 실패를 잡는 검사다. **이 항목을 빼면 안 된다.**)
3. 만드는 도중 [취소]를 누르면 FFmpeg이 실제로 멈추고 반쪽짜리 파일이 남지 않는다.
4. 진행률이 0에서 100까지 실제 진척에 따라 올라간다 (타이머 흉내가 아니다).

### 단계 3 — 미리보기가 사진 프로젝트에서 동작한다 (1일)

- 미리보기 상자에 `<img>` 층 추가, 시각→사진 고르기
- `<video>` 가 없을 때의 시계
- `sourceDimensions()` 가 캔버스 크기로 되돌아가게

**수용 기준**
1. 재생을 누르면 시간이 흐르고, 그 시각의 사진이 미리보기에 바뀌어 나온다.
2. 화면비를 9:16 → 16:9 → 1:1 로 바꾸면 **틀이 실제로 바뀌고** 잘릴 부분이 어둡게 보인다.
3. **자막을 마우스로 끌 수 있고**, 끈 자리와 내보낸 영상의 자리가 같다. 확인 방법은 Phase 3에서 쓴 것과 동일하게 — 검은 배경에 새겨 글자 픽셀의 무게중심을 재고 설정값과 대조 (오차 1% 이내).
   *(`memory/preview-must-use-the-output-frame.md` 가 기록한 결함이 재발하는지 보는 검사다.)*

### 단계 4 — 사진 영상에 자막을 얹는다 (0.5일)

- `slideshow.py` 에 ASS 자막 필터 연결 (2.4에서 명령은 이미 실측 확인)

**수용 기준**
1. 사진 프로젝트에서 자막을 여러 개 만들고 [내보내기 → 자막 입힌 영상]이 **잠기지 않고** 동작한다.
2. 만들어진 영상의 프레임을 뽑아 **한글이 네모(□)가 아님**을 눈으로 확인한다.
3. 프로젝트 이름을 `사진, 시험;[a]'b` 처럼 지어도 렌더링이 성공한다 (`memory/ffmpeg-filter-path-escaping.md` 회귀 검사).

### 단계 5 — 음원 영상 (1.5일)

- mp3 프로젝트에서 `<video>` 를 소리 재생기로 쓰기
- 가사 붙여넣기 → 줄 단위 자막
- 자막 줄 ↔ 사진 짝짓기(`seg_id`)와 화면
- 렌더링 직전 `seg_id` → `duration` 변환, `-shortest`

**수용 기준**
1. mp3를 넣고 재생하면 **소리가 나고 시간이 흐른다.**
2. **두드려 맞추기를 켜고 스페이스바를 눌러** 가사 3줄의 시작 시각을 찍을 수 있다 (실제로 눌러서 확인).
3. 사진 3장을 가사 3줄에 각각 짝지은 뒤 내보내면, 만들어진 영상의 길이가 **음원 길이와 0.1초 이내**로 같다.
4. **각 가사 줄이 시작되는 순간에 사진이 바뀐다** — 각 가사 시작 +0.1초 지점의 프레임 색이 짝지은 사진과 같음을 측정으로 확인한다.
5. 사진 수와 가사 줄 수가 다를 때 무슨 일이 벌어지는지 **내보내기 전에 한국어로 알려 준다.**

### 단계 6 — 강제정렬 (1.5일, 그중 0.5일은 실험)

- **먼저 실험**: `tests/sample/` 음성으로 인식 결과와 정답 대본을 대조해 정확도를 잰다. 이 결과를 보고 진행 여부를 사용자와 다시 정한다.
- `stt.transcribe()` 반환값에 `words` 추가
- `app/core/align.py` 신규 (difflib 대조 + 비례 배분)
- 왼쪽 패널에 대본 칸 + [시간 붙이기]

**수용 기준**
1. 샘플 영상의 **정확한 대본**을 붙여넣고 [시간 붙이기]를 누르면 자막이 시각과 함께 만들어진다.
2. 같은 영상을 음성인식만으로 만든 자막과 견주어, **문장별 시작 시각 차이의 중앙값이 0.3초 이내**다.
3. **짝을 못 찾아 짐작한 줄이 화면에 표시되고**, 그 줄만 두드려 맞추기로 고칠 수 있다.
4. 대본에 숫자("2024년")가 들어간 문장을 일부러 넣어, 프로그램이 죽지 않고 그 줄을 "짐작함"으로 표시하는지 확인한다.

### 단계 7 — 자막→대본 마무리 (0.25일)

**수용 기준**
1. [자막을 대본으로]를 누르면 "나레이션을 만들면 지금 자막 시각이 새로 계산됩니다"라고 **미리 알려 준다.**
2. 목소리 교체 흐름에서 원본 소리 볼륨 기본값이 0%가 된다.
3. `docs/PRD.md` 의 F-44 상태 표기를 실제(구현 완료)에 맞게 고친다.

### 합계

| 단계 | 소요 | 난이도 |
|---|---|---|
| 1 사진 통로 | 0.5일 | 하 |
| 2 사진→영상 | 1일 | 중 |
| 3 미리보기 | 1일 | 중상 |
| 4 사진+자막 | 0.5일 | 하 |
| 5 음원 영상 | 1.5일 | 중 |
| 6 강제정렬 | 1.5일 | 중 (품질은 미지수) |
| 7 자막→대본 | 0.25일 | 하 |
| **합계** | **약 6.25일** | |

순서 조정 여지: **단계 6·7은 1~5와 서로 의존하지 않는다.** 강제정렬을 먼저 하고 싶으면 그래도 된다. 반대로 1~5는 반드시 순서대로다.

## 7. 위험 요소와 아직 모르는 것

### 위험 (근거가 있는 것)

| # | 위험 | 근거 | 대응 |
|---|---|---|---|
| R-1 | **크기가 다른 사진을 concat 데먹서에 넣으면 오류 없이 틀린 영상이 나온다** — 마지막 사진만 되풀이되고 길이도 어긋난다 | [실측] 3장 시험에서 t=1/4/7초 전부 마지막 사진 색, 길이 8.0초(기대 9.04초), 종료 코드 0 | 정규화를 필수 단계로. **완성 후 프레임 색을 재는 자동 점검**을 수용 기준에 넣음 (단계 2-②) |
| R-2 | **`-loop 1` 방식은 사진 수십 장에서 메모리 부족으로 죽는다** | [실측] 60장에서 `Cannot allocate memory`, `-filter_complex_script` 로 바꿔도 동일 | 방법 ㉰(정규화 후 concat)로 간다. 시험을 3장이 아니라 **30장 이상**으로 |
| R-3 | **영상 없는 프로젝트에서 자막 위치가 결과와 어긋난다** | `sourceDimensions()` 가 null → `outputFrameRect()` 가 무력화 [확인됨]. 같은 결함이 과거에 438픽셀 어긋남을 냈다 (`memory/preview-must-use-the-output-frame.md`) | 캔버스 크기로 되돌아가게 하고, **그리는 쪽과 끄는 쪽을 짝으로** 확인 |
| R-4 | concat 목록의 마지막 항목 때문에 영상이 의도보다 길어진다 | [실측] 기대 120.0초 / 실제 122.0초 | 완성 후 길이를 ffprobe로 재는 것을 수용 기준에 넣음 |
| R-5 | 사진마다 파일을 하나씩 새로 만들므로 디스크가 찬다 | [실측] 60장 정규화 3.8초, 파일 60개 생성 | 캐시 + 정리 규칙을 정한다 |
| R-6 | 강제정렬 정확도가 쓸 만하지 않을 수 있다 (숫자·영어 표기 차이) | 근거 없음 — **재 보지 않았다** | 만들기 전에 반나절 실험 (단계 6 앞부분) |
| R-7 | 진입점이 2개에서 4개로 늘면 시작 화면이 복잡해진다 | 판단 | 카드를 한 줄로 같은 크기로 놓아 "고르는 일"이 하나로 보이게 |

### 아직 모르는 것 (전부 **[확인 안 함]**)

1. **휴대폰 사진의 회전 정보(EXIF Orientation).** 세로로 찍은 사진이 가로로 눕거나 반대로 나올 수 있다. FFmpeg이 이걸 어떻게 다루는지 **이번 조사에서 확인하지 않았다.** 실제 휴대폰 사진 몇 장으로 반드시 시험할 것.
2. **아이폰 사진(.heic).** 이 FFmpeg 빌드의 해독기 목록에 HEIF/HEIC 이미지 해독기가 보이지 않았다 (hevc **영상** 해독기만 있다) [확인됨]. 아이폰에서 바로 꺼낸 사진은 못 읽을 가능성이 높지만 **실제 heic 파일로 시험하지 않았다.** 안 되면 "아이폰 사진은 먼저 jpg로 바꿔 주세요"라고 안내해야 한다.
3. **사진 100장 이상.** 60장까지만 쟀다. 정규화가 사진 수에 비례하므로 100장이면 약 6~7초일 것으로 보이지만 [산술 추정], 실제 휴대폰 사진(장당 3~5MB, 4000×3000)은 시험용 단색 이미지보다 훨씬 무겁다.
4. **흐린 배경 여백 채우기를 사진에 적용했을 때.** `framing.py` 의 `split/gblur/overlay` 필터를 **사진 입력으로는 돌려보지 않았다.**
5. **전환 효과(xfade).** 필터가 존재한다는 것만 확인했다. 사진 수십 장에서의 성능·메모리는 전혀 모른다.
6. **mp3 프로젝트에서 두드려 맞추기가 실제로 동작하는지.** 코드상 될 것으로 보이지만 **눌러 보지 않았다.**
7. **강제정렬의 실제 정확도.** 전혀 재지 않았다.
8. 정규화 중간 파일을 jpg로 둘지 png로 둘지. jpg로 실측했고 화질 손실이 눈에 띄지는 않았지만 **글자가 든 사진(캡처 화면 등)에서는 문제가 될 수 있다** — 확인하지 않았다.

## 8. 조사 중 실행한 명령 (재현용)

이번 조사의 숫자는 아래 순서로 얻었다. 시험용 파일은 임시 폴더에 만들었고 프로젝트 폴더는 건드리지 않았다.

1. `ffmpeg -f lavfi -i color=...` 로 크기가 다른 단색 시험 사진 생성 (1920×1080 / 800×1200 / 640×480 / 3000×2000 등)
2. concat 데먹서 목록에 **jpg+png 섞어** 넣고 실행 → `No JPEG data found in image`
3. concat 데먹서 목록에 **전부 jpg, 크기 다르게** 넣고 실행 → 길이 8.0초, 세 시각 모두 마지막 사진 색
4. `-loop 1 -t N -i` × 3 + `concat` 필터 → 길이 9.000초, 세 시각 색 모두 정확
5. 같은 방식 × 60 → `Cannot allocate memory` (인라인·`-filter_complex_script` 둘 다). 전체 명령 길이 18,950자
6. 사진 60장 정규화(3.8초) → concat 데먹서(11.2초) → 120초 1080×1920 영상. 12개 표본 색 전부 일치
7. 정규화 사진 5장 + 10초 mp3 + `ass=` 자막 + `-shortest` → 정확히 10.000초, 영상·소리 트랙 둘 다
8. `ffprobe -select_streams v:0` 을 jpg와 mp3에 각각 실행 → jpg는 1920×1080, mp3는 빈 목록
9. 900×700 webp를 정규화 → 1080×1920 jpg 정상

## 9. 결정이 필요한 것 (사용자에게 물어야 할 것)

1. **시작 화면 카드를 4개로 늘리는 안**에 동의하는지. (5절 참고. 3개로 줄이는 안도 함께 적어 두었다.)
2. **강제정렬(N-3)을 만들기 전에 정확도 실험 반나절을 먼저 쓸지.** 실험 결과가 나쁘면 "완전 자동" 대신 "두드려 맞추기를 도와주는 보조 도구"로 목표를 낮추는 편이 나을 수 있다. **기능을 빼자는 뜻이 아니다** — 어떤 모습으로 만들지를 정하자는 뜻이다.
3. **사진 전환 효과(스르륵 바뀜)를 이번 범위에 넣을지.** 넣지 않으면 사진이 딱딱 바뀐다. 위험(2.5절)이 있어 이번엔 빼고 나중에 따로 조사하기를 권한다.
4. **정규화 중간 파일을 프로젝트 폴더 안에 남길지, 만들 때마다 지울지.** 남기면 두 번째 내보내기가 빠르고, 지우면 폴더가 깔끔하다.
