## 0. 이 문서의 범위

승인된 다섯 단계 중 **1단계만** 다룬다.

| 넣는 것 | 안 넣는 것 (뒤 단계) |
|---|---|
| ① 효과 띠 **뼈대** (저장 구조·API·타임라인 화면) | 비·눈·물방울·비눗방울·폭죽 |
| ② 화면 **확대/축소** (고정 배율) | 색 보정 필터 |
| ③ **줌 강조** (구간에서 배율이 변함) | 주변 어둡게·부분 흐림·비네트·테두리 |

뼈대를 먼저 세우는 이유: 효과를 하나 얹을 때마다 저장 구조와 화면을 새로 손대면
그때마다 미리보기가 어긋난다. **한 번 세우고 이후 효과는 등록만** 하게 만든다.

## 1. 관통 원칙 — 사용자가 적용한다

사용자 지시: *"효과 기능만 설계하고 사용자가 적용할 수 있도록 하는 거야."*

이 설계 어디에도 **"몇 초에 무엇이 자동으로 들어간다"는 값이 없다.** 효과는 전부
사용자가 타임라인에 막대를 놓아야만 생긴다. 기본 프로젝트의 효과 목록은 **비어 있다.**

## 2. 저장 구조

### 2-1. 화면 확대 — `framing.DEFAULT_OUTPUT` 에 항목 하나 추가

```python
DEFAULT_OUTPUT = {
    "aspect": "source",
    "fit": "crop",
    "focus_x": 50.0,
    "focus_y": 50.0,
    "pad_blur": True,
    "zoom": 1.0,        # ← 새로 추가. 0.5(절반) ~ 2.0(두 배)
}
```

기본값 `1.0` 이므로 **옛 프로젝트를 열어도 지금까지와 똑같이 동작한다.**

### 2-2. 효과 — 프로젝트 파일에 `effects` 배열 추가

```json
"effects": [
  { "id": "fx-1", "kind": "zoom_punch", "start": 12.0, "end": 14.5,
    "strength": "medium", "params": { "focus_x": 50.0, "focus_y": 40.0 } }
]
```

| 칸 | 뜻 | 규칙 |
|---|---|---|
| `id` | 막대 하나를 가리키는 이름 | 서버가 붙인다 |
| `kind` | 효과 종류 | 등록표에 있는 것만. 1단계는 `zoom_punch` 하나 |
| `start` `end` | 몇 초부터 몇 초까지 | `start < end`, 영상 길이 안으로 제한 |
| `strength` | 세기 | `low` / `medium` / `high` 세 가지 |
| `params` | 효과마다 다른 값 | 종류별로 정한다 |

**막대는 여러 개 놓을 수 있고, 겹쳐도 된다.** 이것이 "요소요소 작은 폭죽"을 만드는 방법이다.

## 3. 새 모듈 — `app/core/effects.py`

`CLAUDE.md` 규칙: 외부 명령은 `app/core/` 아래에서만 감싼다. API 라우트는 이 모듈만 부른다.

```
KINDS            효과 등록표 — 종류 이름 → { 한글이름, 기본 params, 필터 만드는 함수 }
normalize(list)  사용자가 보낸 목록을 다듬는다 (시스템 경계 검증)
build_filter(effects, width, height, fps, duration) -> str | None
                 효과 목록 전체를 FFmpeg 필터 문자열 하나로 만든다. 없으면 None
```

**효과를 새로 추가하는 일이 `KINDS` 에 줄 하나 더하는 것으로 끝나야 한다.** 2~5단계에서
효과 열 몇 개를 붙일 것이므로, 이 지점을 좁게 만들어 두는 것이 1단계의 핵심 값어치다.

## 4. 화면 확대/축소 계산

### 4-0. 이 기능이 무엇인가 (사용자 지시 원문에 따름)

> *"16:9 영상에서 9:16 영상으로 변형할 때, 영상을 제대로 만들기 위해 확대할 필요가 있을 때
> 쓰려는 것이다. 그리고 확대하면서 **9:16 사각형을 16:9 영상의 어느 위치에 맞출 것인지**
> 설정할 수 있도록 하려는 것이다. 그냥 확대가 아니다."* (2026-08-14)

즉 이 기능은 **"잘라낼 사각형을 사용자가 다룬다"** 는 하나의 기능이고, 다루는 것이 둘이다.

| 다루는 것 | 무엇을 정하나 | 지금 상태 |
|---|---|---|
| **크기** | 세로 사각형을 얼마나 작게(=화면을 얼마나 크게) 할 것인가 | ❌ **없다.** 사각형이 화면 높이를 꽉 채운 크기로 고정 |
| **위치** | 그 사각형을 원본의 어디에 놓을 것인가 | ✅ **있다.** 마우스로 끌기(`app.js` 3360~3364행) + 슬라이더(3317~3321행) |

**그러므로 이 작업은 "위치 기능에 크기를 더하는 것"이다.** 위치를 새로 만들지 않는다.

### 4-1. 한 문장 정의

> **출력 영상의 크기는 확대와 무관하게 지금과 똑같다.
> 확대는 "그 틀 안에 원본의 얼마만큼을 담을 것인가"만 바꾼다.**

`보이는 영역 = 기준 잘라내기 영역 ÷ zoom`

- `zoom = 2.0` → 절반만 담긴다 = **두 배로 커 보인다**
- `zoom = 0.5` → 두 배 넓게 담긴다 = **절반으로 작아 보인다** (원본을 벗어나면 여백)

출력 크기를 고정하는 이유가 중요하다. 자막 글자 크기는 **출력 틀의 세로 픽셀** 기준으로
계산된다(`style_map.to_ass_style`). 확대할 때마다 출력 크기가 변하면 **자막 크기가 같이
출렁인다.**

### 4-2. FFmpeg 필터

| 경우 | 필터 |
|---|---|
| `zoom = 1.0` | 지금과 동일 (`crop=...` 또는 pad 필터) |
| `zoom > 1.0` | `crop=cw:ch:x:y,scale=W:H` — 좁게 잘라 출력 크기로 늘린다 |
| `zoom < 1.0` | `crop=...,scale=w2:h2,pad=W:H:(W-w2)/2:(H-h2)/2` — 잘라낸 것을 작게 줄이고 남는 자리를 채운다. `pad_blur` 가 켜져 있으면 검정 대신 흐린 원본 |

`cw = _even(base_crop_w / zoom)`, `ch = _even(base_crop_h / zoom)`.
잘라낼 자리 `x`, `y` 는 지금과 같이 `focus_x/focus_y` 가 정한다.

### 4-3. 화질 경고 (반드시 넣는다)

실측: 1280×720 을 세로 9:16 으로 자르면 **이미 가로 화소의 32%** 만 쓴다.
1.6배 더 당기면 20%만 쓰고 선명도가 1.13 → 0.67 로 **41% 떨어진다.**

- 상한 **2.0** · 하한 **0.5** 로 `normalize()` 에서 자른다
- `resolve()` 가 `sharpness = crop_w / out_w` 를 함께 돌려준다
- 화면은 `sharpness < 0.75` 이면 **"이 배율에서는 화면이 흐려집니다"** 를 노랑으로 띄운다

### 4-4. 반드시 짝으로 고칠 세 곳

`memory/preview-must-use-the-output-frame.md` — 여기서 이미 **438픽셀 어긋남** 사고가 났다.

| 파일 | 무엇을 |
|---|---|
| `app/core/framing.py` | `resolve()` 에 zoom 반영 (원본) |
| `app/static/app.js` | `resolveFraming()` 에 **똑같이** 반영 (사본) |
| `tests/phase4_test.py` | node 로 `app.js` 를 돌려 서버와 대조하는 240가지에 **zoom 축 추가** |

**좋은 소식**: `outputFrameRect()` 는 `frame.crop` 을 그대로 쓰므로(app.js 1362~1367행),
확대를 "crop 영역이 작아지는 것"으로 표현하면 **미리보기 틀과 자막 끌기가 저절로 따라온다.**
`outputFrameRect()` 자체는 손대지 않아도 된다 — 다만 **점검으로 확인**한다.

### 4-5. ⚠️ 확대를 넣으면 지금 화면이 깨진다 — 위치 슬라이더가 한 개다

**코드를 읽고 찾은 것이다. 실제로 겪기 전에 미리 막는다.**

지금은 16:9 를 9:16 으로 자를 때 사각형이 **화면 높이를 꽉 채운다.** 그래서 위아래로는
움직일 자리가 없고, **움직일 수 있는 축이 언제나 하나뿐**이다. 화면은 이 사정에 맞춰
슬라이더를 **한 개만** 두고, 어느 축을 조절할지 자동으로 고른다:

```js
// app.js 3278~3279행
const vertical = frame.fit === "crop" && frame.crop && (dims.h - frame.crop.h) > 0;
slider.value = String(vertical ? conf.focus_y : conf.focus_x);
```

**확대를 넣는 순간 이 전제가 무너진다.** 사각형이 세로로도 작아지므로 **가로·세로 둘 다
움직일 수 있게 되는데, 슬라이더는 하나라서 한쪽 축이 잠긴다.** 오류는 나지 않는다 —
사용자가 "위아래로 안 움직여지네"라고 느낄 뿐이다. 이 프로젝트에서 가장 자주 나온
**"오류 없이 틀린 결과"** 유형이다.

**고치는 방법**: 위치 슬라이더를 **가로·세로 두 개**로 나눈다. 움직일 자리가 없는 축
(`slack == 0`)은 흐리게 하여 왜 못 움직이는지 보이게 한다. 마우스 끌기는 이미 두 축을
따로 계산하고 있으므로(`slackX`·`slackY`, 3360~3364행) **손댈 것이 없다.**

**점검**: `zoom > 1` 에서 `focus_x` 와 `focus_y` 를 **각각** 바꿨을 때 잘라내는 자리가
**둘 다** 실제로 움직이는지 잰다 (T11).

## 5. 줌 강조 (`zoom_punch`)

구간 안에서 배율이 **부드럽게 커졌다가 돌아온다.**

| 세기 | 최대 배율 |
|---|---|
| 약하게 | 1.15배 |
| 보통 | 1.35배 |
| 많이 | 1.60배 |

간격 1.17배·1.19배 — **가짜 선택지 기준(1.3배)에 못 미친다.** 배율만으로는 부족하므로
`memory/options-must-actually-differ.md` 규칙에 따라 **잰 값으로 판정**한다. 판정 기준은
배율이 아니라 **화면에서 실제로 커지는 픽셀 양**으로 삼고, 못 넘으면 값을 벌린다.

### ⚠️ 먼저 실측할 것 (이것부터 한다)

FFmpeg 에서 시간에 따라 배율을 바꾸는 내장 수단은 **`zoompan` 이 사실상 유일하다**
(`crop` 은 가로·세로에 시간식을 못 쓰고, `scale` 도 마찬가지다).

`zoompan` 에는 알려진 함정이 둘 있다:

1. **기본 `fps=25`** 라서 30fps 영상에 그냥 쓰면 프레임을 다시 만들어 **움직임이 끊긴다**
2. **`d`(머무는 프레임 수) 기본값이 1이 아니어서** 같은 프레임이 되풀이될 수 있다

→ 구현 전에 **30초 시험 영상으로 프레임 수와 시각을 재서** `fps=원본fps`, `d=1` 로
해결되는지 확인한다. 안 되면 그 자리에서 사용자에게 알리고 대안을 정한다.
이것은 `RESEARCH_screen_effects.md` 에서 재지 않은 새 영역이다 — **증거가 없다.**

## 6. 필터 순서와 구간 적용

### 6-1. 순서

```
[화면비 자르기 + 확대] → [효과] → [자막 새기기]
```

**자막이 맨 마지막**이어야 한다. 효과가 자막 위에 오면 글자가 가려진다.

> 조사 문서는 `[효과] → [자르기] → [자막]` 순서로 쟀다. 여기서는 **효과를 자르기 뒤로
> 옮긴다** — 효과 레이어를 출력 크기(더 작음)로만 만들면 되어 빠르기 때문이다.
> **순서를 바꾸었으므로 자막이 살아남는지 다시 재야 한다.**

`framing.chain()` 이 이미 "필터를 순서대로 잇는" 일을 한다. 가운데에 효과를 끼운다.

### 6-2. 구간에만 거는 방법

`overlay` · `blend` 같은 합성 필터는 `enable='between(t,시작,끝)'` 를 지원한다.
효과 레이어는 계속 만들되 **합성만 구간 안에서** 켠다.

`zoompan` 은 `enable` 을 지원하지 않으므로 배율식 안에 구간을 넣는다:
`z='if(between(it,시작,끝), 1+세기*곡선, 1)'`

### 6-3. `-vf` 에서 `-filter_complex` 로

효과가 하나라도 있으면 생성 필터(`color=` 등)를 써야 하므로 `-filter_complex` 가 필요하다.
자막(`ass`)도 같은 `-filter_complex` 안에 넣을 수 있다 — 조사에서 **확인했다**
(자막 자리 밝은 픽셀 11,725개 생존).

**효과가 없으면 지금과 똑같이 `-vf` 를 쓴다.** 기존 경로를 건드리지 않는다.

## 7. 화면 (UI)

### 7-1. 잘라낼 사각형 다루기 (확대 + 위치)

화면비 설정 칸을 **"잘라낼 자리"** 한 덩어리로 묶는다. 세 줄이다.

```
확대     [────●────────]  1.0배          ← 0.5 ~ 2.0. 사각형의 크기
         ⚠ 이 배율에서는 화면이 흐려집니다   ← sharpness < 0.75 일 때만

가로 위치 [──────●──────]  50%           ← 움직일 자리가 없으면 흐리게
세로 위치 [──────●──────]  50%           ← 확대해야 살아난다
```

그리고 **미리보기 위의 사각형을 마우스로 바로 끌 수 있다** (이미 되고 있다).
슬라이더와 마우스 끌기는 **같은 값**(`focus_x`·`focus_y`)을 만지므로 서로 따라 움직인다.

사용자가 실제로 하게 될 일:

1. 화면비를 `세로 9:16` 으로 고른다 → 미리보기에 세로 사각형이 나타난다
2. `확대` 를 올린다 → 사각형이 **작아진다** (= 담기는 화면이 커진다)
3. 사각형을 **마우스로 끌어** 인물이나 보여 주고 싶은 곳에 맞춘다
4. `이 부분 미리보기` 로 실제 결과를 확인한다

### 7-2. 효과 띠

이미 있는 **자막 타임라인 띠(F-25)** 바로 아래에 **효과 띠**를 한 줄 더 놓는다.
자막 띠의 부품(막대 끌기·길이 조절·현재 위치 표시·확대/축소)을 그대로 재활용한다.

- 왼쪽 `효과` 패널에서 종류를 고르면 **현재 재생 위치**에 기본 3초 막대가 생긴다
- 막대를 끌어 옮기고, 끝을 잡아 길이를 바꾼다
- 막대를 고르면 아래에 `세기: 약하게 / 보통 / 많이` 와 효과별 값이 나온다
- 막대는 여러 개 놓을 수 있다

### 7-3. 미리보기 — 흉내 내지 않는다

브라우저에서 CSS 로 효과를 그리지 **않는다**. 같은 난수·같은 흐림을 두 곳에서 똑같이
구현하는 것은 불가능하고, 반드시 결과물과 어긋난다.

**이미 있는 10초 미리보기를 쓴다.** 효과 막대를 고르고 `이 부분 미리보기` 를 누르면 그
구간을 실제로 렌더해 보여 준다 (5초 720p 조각이 **1~2초** — 실측).

### 7-4. 느려짐을 미리 알린다

효과를 넣으면 **약 5.7배 느려진다** (1080p 30초: 3초 → 17초). 효과가 하나라도 있으면
내보내기 단추 옆에 예상 시간을 적는다.

## 12. 2단계 구현 현황 — 비 · 눈 (2026-08-15) ✅ 완료·검증됨

### 12-1. 뼈대가 실제로 값을 했는가

했다. **저장 구조·API·화면·타임라인 띠를 한 줄도 고치지 않았다.** 손댄 파일은
`app/core/effects.py` **하나**뿐이다. 화면의 효과 단추는 `/api/system/effect-kinds` 를
그대로 그리므로 등록표에 항목을 더하자 **단추가 저절로 생겼다**(브라우저로 눌러 확인).

등록표에 갈래를 하나 늘린 것이 전부다:

| 갈래 | 뜻 | 쓰는 효과 |
|---|---|---|
| `build` | 화면 자체를 주무르는 사슬 필터 | 줌 강조 |
| `layer` | 화면 위에 덧씌울 그림 + 켜는 구간 | **비 · 눈** (앞으로 비눗방울·폭죽도) |

### 12-2. 만드는 방법 — 비와 눈은 같은 방법이고 늘리는 방향만 다르다

```
성긴 점을 찍은 작은 그림 → 세로로 세 번 이어 붙이기 → 크게 늘리기
  → 시간에 따라 잘라내는 창을 위로 올리기(=아래로 떨어짐) → 밝기 면에만 screen 합성
```

- **비**: 세로로만 늘린다(`flags=neighbor`) → 가느다란 **줄기**. 실측 세로 16px × 가로 1.0~1.5px
- **눈**: 가로·세로를 같은 배수로 늘린다(`flags=bicubic`) → 둥근 **덩어리**. 실측 둥근 정도 0.97,
  앞뒤 **두 겹**(앞은 크고 빠르고 밝게, 뒤는 작고 느리고 흐리게), 좌우로 흔들림

조사 문서가 권한 "흐린 뒤 밝기를 되살린다"(비)를 **쓰지 않았다.** 늘리기는 밝기를
퍼뜨리지 않으므로 조사에서 넘어진 함정 ①②를 **아예 만나지 않는다.**

### 12-3. 조사 문서의 결론을 두 군데 뒤집었다

| 조사 문서 | 실제로 택한 것 | 이유 |
|---|---|---|
| 합성 전 모든 입력을 `format=gbrp` 로 | **밝기(Y) 면에만 합성**하고 색 면은 원본 그대로 | gbrp 왕복은 효과를 **꺼도** 화소값의 31%를 바꾸고 최대 49까지 밀었다. 밝기만 합성하면 구간 밖이 **완전히 같다** |
| `color=` 로 레이어를 만들고 `shortest=1` | **원본을 `split` 해서** 레이어를 만든다 | 길이·프레임률이 저절로 같아지고, 끝없는 스트림 함정(④)을 아예 만나지 않는다 |

### 12-4. 세기 3단계 (실측, 1280×720)

문턱값(점의 개수)과 진하기를 **함께** 움직였다. 하나만 움직이면 가짜 선택지가 된다.

| | 약하게 | 보통 | 많이 | 단계 간격 |
|---|---:|---:|---:|---|
| **비** | 5.2% | 15.9% | 29.9% | 3.04배 · 1.88배 |

## 13. 3~4단계 구현 현황 — 값 조절 · 색감 · 강조 (2026-08-15) ✅ 완료·검증됨

### 13-1. 효과별 값 조절(슬라이더) 체계를 새로 넣었다

사용자 지시: *"효과 속도를 조절할 수 있도록 설계에 반영해 줘."*

속도만 넣고 끝낼 수도 있었지만, 뒤에 올 효과들이 자리·크기·밝기 같은 값을 저마다
갖는다. 그래서 **값 하나를 슬라이더 하나로 그리는 공통 체계**를 만들었다.

등록표에 값의 **설명서**를 적어 두면 화면이 그대로 슬라이더를 그린다:

```python
"params": {"speed": {"label": "떨어지는 속도", "min": 30, "max": 250,
                     "step": 5, "default": 100, "suffix": "%"}}
```

**화면 코드는 효과 이름을 하나도 모른다.** 새 효과에 값을 붙여도 `app.js` 를 고칠
일이 없다. 브라우저로 눌러 확인했다 — 비를 고르면 속도 슬라이더 하나, 주변 어둡게를
고르면 가로·세로·크기 슬라이더 셋이 나오고, 값이 없는 효과는 칸 자체가 숨는다.

> 고친 것 하나: 예전 `_clean_params` 는 **모든 값을 0~100 으로 잘랐다.** 그대로
> 두었으면 속도를 100% 위로 못 올리고 밝기를 음수로 못 내렸다. 값마다 자기 범위를
> 갖게 바꿨다.

### 13-3. 새로 붙인 효과 10종 (전부 FFmpeg 내장 필터)

| 효과 | 만드는 법 | 조절할 수 있는 값 |
|---|---|---|
| 부분 흐림 | 네모만 오려서 `boxblur` 후 제자리에 `overlay` | 가로·세로 자리, 너비, 높이 |
| 주변 어둡게 | `geq` 로 둥근 마스크를 작게 그려 늘린 뒤 **곱하기** 합성 | 가로·세로 자리, 밝은 부분 크기 |
| 가장자리 어둡게 | `vignette` | — |
| 밝기·대비·채도 | `eq` | 밝기(−100~100), 대비, 채도 |
| 따뜻하게 / 차갑게 | `eq` + `colorbalance` (그림자·중간톤·밝은톤 **셋 다**) | — |
| 선명하게 | `eq` | — |
| 빈티지 | `eq` + `colorchannelmixer`(세피아 섞기) | — |
| 흑백 | `hue=s=0` (+ 많이는 대비 강화) | — |
| 네모 테두리 | `drawbox` | 가로·세로 자리, 너비, 높이 |

**색을 바꾸는 필터에서는 `eq` 를 반드시 앞에 둔다.** 뒤에 두면 색공간 변환이 끼어
구간 밖 화소가 ±2 밀린다(실측). 순서만 바꾸면 차이가 정확히 0이 된다.

### 13-4. 잡은 결함 — 비·눈·주변 어둡게를 걸면 **화면이 흑백이 되었다**

이번 작업에서 가장 중요한 발견이다. 색 면을 원본 그대로 두려고 쓴
`blend=...:c1_opacity=0:c2_opacity=0` 이 **정반대로 동작했다.** `blend` 는 첫 입력이
'위', 둘째가 '아래'인데 `opacity=0` 은 '아래를 쓴다'는 뜻이라, 효과 그림의 중립
색값(128)이 원본 색을 덮었다.

    c1_opacity=0 → 색의 진하기 126.1 → 0.0
    옵션을 뺌     → 126.1 → 126.1

**그때 이미 이 효과를 검사하는 점검 30개 가까이가 전부 통과하고 있었다.** 구간 밖
완전 일치·안개 없음·낙하 방향·세기 3단계·자막 생존·세로 영상까지 다 쟀는데,
그 검사들이 **하나같이 흑백으로 밝기만** 봤기 때문이다. 이제 **색을 따로 재는 검사**를
비·눈과 새 효과 전부에 넣었고, 일부러 되돌려 6개가 실패하는 것을 확인했다.

## 14. 세기 사다리를 다시 잡다 — "화면을 가리면 안 된다" (2026-08-15) ✅ 완료·검증됨

### 14-1. 무슨 일이 있었나

사용자 지적: *"지금 효과들이 화면을 너무 가리고 있다. 영상 화면을 너무 가리게 되면
시청자들이 영상 화면에 집중할 수 없어."*

**옳은 지적이었고, 원인이 코드에 남아 있었다.** 세기 3단계를 정할 때 지킨 기준은
"단계 사이가 1.3배 넘게 벌어질 것"(가짜 선택지 방지) **하나뿐**이었다. 그것은
아래에서 미는 힘만 준다. 위에서 누르는 기준이 없으니 '많이'가 계속 세졌고,
**점검 715개는 전부 통과하고 있었다.** 점검은 "효과가 걸렸는가 · 단계가 구별되는가 ·
구간 밖이 그대로인가"를 물었고 셋 다 맞았기 때문이다. **"이 정도면 과하지 않은가"는
아무도 묻지 않았다.**

### 14-2. 재는 자를 새로 만들었다 — 결(디테일)이 빠져 있었다

밝기와 색만으로는 '가림'이 안 잡힌다. **결**을 반드시 함께 재야 한다. 어둡게 하는
효과는 밝기와 함께 결을 지우고, 비·눈은 결을 **더한다.** 둘 다 나쁘다.

| 재는 것 | 뜻 |
|---|---|
| 덮인 면적 | 밝기가 8 이상 달라진 화소의 비율 |
| 평균 밀림 | 화면 전체 \|Δ밝기\| 평균 (0~255 자) |
| 남은 밝기 | 평균 밝기 비율 — 어둡게 하는 효과용 |
| **남은 결** | 이웃 화소와의 차이 평균의 비율 ← **이것이 빠져 있었다** |

**재는 바탕도 문제였다.** 그때 쓰던 샘플과 데모 원본이 전부 색막대였다(국소대비
0.69~0.71). 평평한 색막대 위에서는 결이 없어 '결을 얼마나 흐트러뜨리는가'를 아예
잴 수 없다. 결·중간 밝기·적당한 색을 갖춘 화면(국소대비 7.08)을 만들어 쓰자
비로소 드러났다.

### 14-3. 세운 상한

| 세기 | 평균 밀림 | 남은 밝기 | 남은 결 |
|---|---:|---:|---:|
| 약하게 | ≤ 4 | ≥ 90% | 92~112% |
| 보통 | ≤ 9 | ≥ 78% | 88~125% |
| 많이 | ≤ 18 | ≥ 62% | 80~140% |

**단계 간격 1.3배 이상은 그대로 지킨다.** 두 기준을 동시에 만족시키려면 값을 그냥
낮추는 것이 아니라 **비율을 유지한 채 사다리 전체를 내려야** 한다 — 전 단계에 같은
배수를 곱하면 간격이 보존된다.

상한을 두지 않는 것과 그 이유(빠뜨린 것이 아니라 일부러 뺀 것이다):
줌 강조(덮는 것이 아니라 옮긴다) · 밝기·대비·채도(사용자가 직접 정한다) ·
흑백(색을 빼는 것이 목적이고 결은 지우지 않는다) · 부분 흐림·네모 테두리(정한 자리만).

### 14-4. 무엇을 얼마나 낮췄나 (실측, 결이 있는 화면)

| 효과 | 세기 | 전 → 후 (평균 밀림) | 전 → 후 (남은 밝기·결) |
|---|---|---|---|
| 주변 어둡게 | 많이 | 70.6 → **38.9** | 밝기 38% → **66%** |
| 주변 어둡게 | 약하게 | 39.7 → **14.7** | 밝기 65% → **87%** |
| 가장자리 어둡게 | 많이 | 63.9 → **35.9** | 밝기 44% → **69%** |
| 비 | 많이 | 15.8 → **6.4** | 결 193% → **139%** |
| 눈 | 많이 | 12.4 → **7.4** | 결 120% → **110%** |

### 14-5. 낮추다가 **반대쪽 함정에 빠졌다** — 두 기준은 함께 재야 한다

한 번에 못 맞췄다. 처음 낮춘 값은 **비·눈의 '약하게'를 아무 일도 안 하게** 만들었다
(평균 밀림 0.00). 가짜 선택지를 피하려던 기준을 스스로 어긴 것이다. 그리고
`density`(빗방울 문턱값)는 **절벽처럼** 동작한다 — 0.715 에서는 점이 남고 0.724 에서는
하나도 안 남는다. 그래서 개수는 좁게 움직이고 진하기로 단계를 벌렸다.

### 14-6. 점검이 **틀린 잣대를 쓰고 있었다**

주변 어둡게의 "세 단계가 1.3배 넘게 벌어진다"가 실패했는데, 값이 잘못된 것이 아니라
**점검의 식이 틀렸다.** 남은 밝기끼리 나누고 있었다(63/47 = 1.34배). 그것은
'어두워지는 정도'가 아니다 — 효과가 셀 때만 우연히 1.3을 넘고, 순해지면 사다리가
잘 벌어져 있어도 1에 가까워진다. **어두워진 양**으로 고치자 1.73·1.56배가 되었다.

점검에 새로 넣은 것: `tests/looks_test.py` 5절 "화면을 가리지 않는가"(22개). 결이 있는
화면을 따로 만들어 위쪽 상한과 아래쪽 바닥을 함께 잰다. **옛 값으로 되돌려 정확히
3개가 실패하는 것까지 확인했다**(둘레 밝기 33%, 화면 밝기 38%, 남은 결 194%).

## 15. 5단계 구현 현황 — 물방울 · 비눗방울 · 작은 폭죽 (2026-08-15) ✅ 완료·검증됨

### 15-1. 인수인계 문서의 계획이 틀렸다 — 구조를 바꿀 필요가 없었다

앞 문서는 이렇게 적었다: *"그림을 겹치려면 `-i` 를 더 붙이고 `-filter_complex` 로
옮겨야 하며, 그때 소리 흐름(`-c:a copy`)과 자막 필터가 살아남는지 다시 재야 한다."*

**실측해 보니 그럴 필요가 없었다.** FFmpeg 의 `movie` 소스 필터는 필터그래프 **안에서**
파일을 연다. 지금의 `-vf` 한 줄 구조를 한 군데도 안 건드린다.

| 물어본 것 | 결과 |
|---|---|
| `movie=` 가 `-vf` 안에서 되는가 | 됨 |
| `displace`·`overlay` 가 `enable` 을 받는가 | 됨 — 구간 밖 **다른 값 0개** |
| 자막·소리 복사와 함께 써도 되는가 | 됨 — 소리 살아 있고 자막 글자 새겨짐 |
| 정지 그림을 흘려보내면 시간식이 사는가 | 됨 — `loop`+`setpts`, **0.3초에 렌더 끝남** |

### 15-2. 만드는 법

| 효과 | 파이썬이 그리는 것 | FFmpeg 이 하는 일 |
|---|---|---|
| 물방울 맺힘 | 굴절 지도 2장 + 반짝임 1장 | `displace` 로 화면을 휘게 하고 반짝임을 얹는다 |
| 비눗방울 | 고리 그림 1장 (세로 두 겹) | `overlay` 의 **자리를 시간식으로** 올린다 |
| 작은 폭죽 | 장면 30개를 세로로 이어 붙인 1장 | `crop` 으로 시각에 맞는 칸을 잘라 얹는다 (만화책 넘기기) |

경로는 **파일 이름만** 필터에 넣는다. FFmpeg 이 그림이 있는 폴더(자막과 같은 폴더)에서
실행되기 때문이다. 그래서 필터 문자열에 콜론·쉼표가 아예 없다.

### 15-3. 잡은 결함 둘

**① 물방울이 화면의 71%를 건드렸고 세기를 올려도 71% 그대로였다.**

그림 파일의 밝기는 0~255 인데 필터 안으로 들어오면 **16~235 로 눌린다.** 그래서
128 로 그린 '안 밂'이 필터 안에서 126 이 되어 **온 화면이 2픽셀씩 밀렸다.** 방울보다
그 밀림이 훨씬 커서 세기를 바꿔도 수치가 안 변한 것이다.

    지도를 통째로 128 로 채우고 재기 — 다른 값이 0이어야 정상
      그대로 넘김                 663,681개  ❌
      lutyuv 로 자를 되돌림             0개  ✅

비·눈이 문턱값에서 겪은 것과 **똑같은 함정**이다(ffmpeg-effect-layer-traps ③-c).
`format=yuv420p,lutyuv=y='(val-minval)*255/(maxval-minval)'` 로 자를 되돌려 고쳤다.
고친 뒤 5.0% → 8.7% → 15.5% 로 세기를 따라간다.

> 중간에 **확인 방법에 한 번 속았다.** 지도의 Y 값을 확인하려고 `-pix_fmt gray` 로
> 뽑아 봤더니 128 이 나와 "범위 문제가 아니다"라고 결론 냈다. 그 확인 경로가 범위를
> 되돌리는 변환을 거쳤기 때문이다. 값을 126~130 으로 바꿔 가며 **밀림이 0이 되는 값**을
> 직접 찾아서야 130 이라는 것을 알았다.

**② 비눗방울이 위가 아니라 아래로 가라앉았다** (초당 72픽셀, 설정 속도 70과 일치).

화면의 한 줄 r 에 보이는 것은 그림의 (r − y) 줄이므로 y 가 커지면 그림이 **아래로**
흐른다. `-H + mod(...)` 를 `-mod(...)` 로 고쳤다. 비가 하늘로 솟았던 것과 같은 실수다.

> 이것도 **처음 검증에서는 "위로 간다"고 나왔다.** 밝아진 자리의 무게중심으로 쟀는데,
> 화면 가득한 무늬는 무게중심이 늘 가운데라 방향을 못 잡는다. 비 점검이 쓰는
> **무늬 맞춰보기**(여러 칸 굴려 가장 잘 맞는 것을 찾기)로 바꾸자 방향과 속도가
> 정확히 나왔다.

## 16. 진하기 슬라이더 · 크기 축소 · 색 결함 수정 (2026-08-15 저녁) ✅ 완료·검증됨

### 16-1. 사용자 지시 4건

데모 두 편을 본 사용자가 지시했다. 원문 그대로다:

> 1. 고친 가림에 투명 정도를 사용자가 설정하도록 해줘
> 2. 물방물 맺힘, 물방울 원을 좀 작게
> 3. 비눗방울 원도 조금만 더 작계
> 4. 폭죽도 아주 작게

### 16-2. 진하기(투명 정도) — 색감 값을 **숫자 설명서**로 바꿔야 했다

14절에서 값을 낮춘 9종(주변 어둡게·가장자리 어둡게·비·눈·따뜻하게·차갑게·
선명하게·빈티지·흑백)에 `진하기` 슬라이더를 붙였다. 기본 100%(=14절의 순한 값),
범위 20~200%.

**막힌 곳이 하나 있었다.** 색감 계열은 등록표에 필터 문자열을 **글자 그대로**
적어 두고 있었다(`"eq=saturation=1.15"`). 사람이 읽기에는 좋지만 **진하기를 곱할
수가 없다.** 그래서 필터 이름과 값만 적는 형태로 바꿨다:

```python
"high": {"look": [("eq", {"saturation": 1.15}),
                  ("colorbalance", {"rs": 0.12, "rm": 0.17, ...})]}
```

그리고 값마다 **아무 일도 안 하는 값(중립값)** 을 알면 진하기를 한 줄로 계산할 수 있다:

    새 값 = 중립값 + (적어 둔 값 - 중립값) × 진하기

중립값은 필터마다 다르다 — `eq` 의 채도·대비는 1, `colorbalance` 는 0, `hue` 의 s 는 1,
`colorchannelmixer` 는 **단위행렬**(자기 색 1, 남의 색 0)이다. 이 한 규칙이 6종을 모두
덮는다. 곱셈이므로 **세기 3단계 사이의 비율은 저절로 보존된다.**

비·눈은 레이어 밝기에, 주변 어둡게는 **어두워지는 정도**에 곱한다
(dim 자체에 곱하면 진하기를 올릴수록 밝아지는 거꾸로 된 손잡이가 된다).

실측 — 진하기 50% / 100% / 200% 의 평균 밀림 (세기 '많이', 결이 있는 화면):

| 효과 | 50% | 100% | 200% | 간격 |
|---|---:|---:|---:|---|
| 주변 어둡게 | 18.6 | 37.4 | 73.7 | 2.01·1.97배 |
| 가장자리 어둡게 | 10.4 | 35.9 | 82.3 | 3.45·2.30배 |
| 비 | 3.1 | 6.1 | 11.9 | 1.98·1.97배 |
| 눈 | 3.8 | 7.4 | 13.8 | 1.98·1.86배 |
| 따뜻하게 | 6.3 | 12.4 | 23.7 | 1.97·1.92배 |
| 차갑게 | 5.6 | 11.3 | 22.7 | 2.00·2.02배 |
| 선명하게 | 5.5 | 9.6 | 17.8 | 1.76·1.84배 |
| 빈티지 | 6.0 | 13.0 | 27.0 | 2.16·2.08배 |
| 흑백(약하게) | 3.3 | 6.4 | 11.8 | 1.95·1.84배 |

흑백만 '약하게'에서 잰다. '보통'·'많이'는 이미 채도가 0이라 진하기를 100% 위로
올려도 **더 뺄 색이 없다**(실측 1.00배). 가짜 손잡이가 아니라 물리적인 끝이고,
아래쪽으로는 정상으로 움직인다.

**기본값 100%를 점검이 못 박는다.** 기본값을 올리면 14절의 가림 상한 점검이 더 진한
값을 재게 되어 그 작업이 통째로 무의미해지기 때문이다.

### 16-3. 크기를 줄였다 — 개수·알갱이를 **함께** 움직여야 한다

| 효과 | 무엇을 | 함께 고친 것 |
|---|---|---|
| 물방울 맺힘 | 지름 `min/17 → min/21` (0.81배) | 개수 `9·19·34 → 12·25·44`. 방울이 작아지면 덮는 면적이 0.66배로 줄어 **사다리가 통째로 내려앉는다** |
| 비눗방울 | 지름 `min/42 → min/50` (0.84배) | 개수는 그대로. "조금만"이라 했고 셋 중 존재감이 가장 컸다 |
| 작은 폭죽 | 칸 크기 기본 `38 → 22`(하한 15→10) | 알갱이 굵기 `칸/28 → 칸/20`. **칸만 줄이면 알갱이가 다시 점으로 사라진다**(15-5절에서 이미 한 번 겪었다) |

실측 (평균 밀림, 약하게·보통·많이):

| 효과 | 전 | 후 |
|---|---|---|
| 물방울 맺힘 | 1.41 · 2.61 · 5.04 | **1.06 · 2.42 · 4.05** |
| 비눗방울 | 0.25 · 0.94 · 2.30 | **0.17 · 0.67 · 1.67** |
| 작은 폭죽 | 0.10 · 0.18 · 0.26 | **0.07 · 0.13 · 0.18** |

단계 간격 1.3배와 구간 밖 완전 일치는 셋 다 유지된다.
**데모를 눈으로 확인했다** — 셋 다 확실히 작아졌고, 셋 다 여전히 잘 보인다.

### 16-4. ★ 데모를 보다가 잡은 결함 — 주변 어둡게가 화면을 **보라색으로** 물들였다

진하기 데모를 만들어 프레임을 보니 주변 어둡게가 화면을 보라·자주색으로 물들이고
있었다. **진하기 200%뿐 아니라 기본값 100%에서도 그랬다.** 이번에 만든 것이 아니라
원래 있던 결함이고, 진하기 슬라이더가 그것을 드러낸 것이다.

**원인.** 주변 어둡게는 회색 그림을 **밝기(Y) 면에만 곱하고** 색(U·V) 면은 원본
그대로 두고 있었다. 그런데 빨강과 파랑의 차이는

    R - B = 1.402(V-128) + 1.772(U-128)

이라 **밝기와 아무 상관이 없다.** 그러니 밝기를 반으로 줄이면 '밝기에 견준 색'이
두 배가 된다. 어두운 곳일수록 색이 진해지는, 실제 사진과 정반대의 그림이 나온다.

**고친 방법 — 검은 그림을 알파(투명도)로 얹는다.** 알파 합성은 색차도 함께 데려간다:

    U_새 = U×(1-a) + 128×a = 128 + (U-128)×(1-a)

`geq` 로 알파만 그리고(`lum=16:cb=128:cr=128:a='...'`) `overlay` 로 얹는다. 실측:

| 방식 | 진하기 | 남은 밝기 | **색의 진하기** | 구간 밖 |
|---|---|---:|---:|---:|
| 밝기만 곱하기 | 100% | 65% | **150%** ❌ | 0 |
| 밝기만 곱하기 | 200% | 34% | **218%** ❌ | 0 |
| 알파로 얹기 | 100% | 71% | **101%** ✅ | 0 |
| 알파로 얹기 | 200% | 42% | **103%** ✅ | 0 |

구간 밖이 원본과 한 값도 다르지 않은 것은 그대로다.

**값을 한 번 더 잡아야 했다.** 알파 합성은 두 기준을 서로 반대로 움직인다 —
화면 전체 평균 밝기는 **더 밝게**(검정 바닥이 16이라서), 둘레 밝기는 **더 어둡게**
(가운데를 완전히 그대로 두므로 대비가 크다) 나온다. 처음에 화면 평균 66%에 맞춰
dim 을 0.49 로 내렸더니 **둘레가 52%까지** 떨어져 점검이 잡았다. 사용자가 실제로
느끼는 것은 둘레이므로 그쪽(≥62%)에 맞춰 **0.86 / 0.73 / 0.60** 으로 정했다.
어두워지는 정도의 간격은 1.94배 · 1.49배다.

**왜 804개가 전부 통과하고 있었나.** 색을 재는 검사가 있긴 했다 — 13-4절에서 화면이
흑백이 되는 결함을 잡고 넣은 것이다. 그런데 그것은 **빨강과 파랑의 절대 차이**로
재고 있었고, 방금 본 대로 그 값은 밝기와 무관해서 **색이 튀어도 그대로다.** 게다가
검사가 묻는 것은 "색이 **사라지지** 않았는가"(아래쪽 기준)뿐이었다. 14절에서 배운
"많을수록 좋다는 값에는 천장을 함께 적어라"를 **색에는 적용하지 않고 있었다.**

새 잣대: **밝기에 견준 색의 진하기** = `(최대채널 - 최소채널) / 최대채널` 의 평균.
어둡게 하는 효과(주변 어둡게·가장자리 어둡게)에 상한 115%를 걸었다. 기본값과
진하기 200% **양쪽에서** 잰다.

### 16-5. 비·눈도 같은 방식으로 고쳤다 (사용자 지시)

주변 어둡게를 고친 뒤 사용자가 *"비눈도 동일하게"* 라고 지시했다. 같은 뿌리의
현상이 밝히는 쪽에도 있었기 때문이다 — `screen` 은 밝기만 올리므로 **밝아진 화소가
원래 색을 그대로 지닌다.** 그래서 풀밭 위의 빗줄기가 초록빛으로 보였다. 흰 비가
아니라 '밝아진 풀'이 된 것이다.

**고친 방법**: 흰 그림에 `alphamerge` 로 알파를 붙여 `overlay` 로 얹는다.
`alphamerge` 는 둘째 입력의 밝기를 첫째 입력의 알파로 삼으므로, **지금 쓰던 회색
그림을 한 글자도 안 고치고** 그대로 알파로 쓸 수 있었다.

```
split=2[w][m];
[w]lutyuv=y=maxval:u=128:v=128,format=yuva420p[white];
[m]<지금까지의 비 그림>[mask];
[white][mask]alphamerge
```

흰색은 `maxval` 로 적는다. 235 처럼 숫자로 적으면 필터 안의 밝기 자가 달라 깨진다.

실측 — **밝아진 자리만** 골라 잰 색의 진하기(낮을수록 흰색):

| 효과 | 진하기 | 예전 `screen` | 지금 알파 |
|---|---|---:|---:|
| 비 | 100% | 20.9% | **15.4%** |
| 비 | 200% | 18.0% | **13.4%** |
| 눈 | 100% | 18.6% | **13.3%** |
| 눈 | 200% | 14.3% | **8.9%** |

(화면 전체로 재면 빗줄기가 차지하는 넓이가 작아 묻힌다. 그래서 이 결함을 아무
검사도 못 잡고 있었다. 새 잣대는 **밝아진 화소만** 골라 잰다. 상한 17%.)

**값을 어떻게 다시 잡았나 — 비는 그대로, 눈만 올렸다.**

알파는 눈송이·빗줄기를 순백으로 바꾸는데 `screen` 은 배경 밝기에 비례해 밝혔으므로,
같은 값에서 평균 밀림이 줄어든다. 그런데 **남은 결은 거의 그대로였다**:

| 효과 | 평균 밀림 (전 → 후) | 남은 결 (전 → 후) |
|---|---|---|
| 비 '많이' | 6.05 → 3.54 | 136% → **132%** |
| 눈 '많이' | 7.43 → 5.13 | 110% → **108%** |

**남은 결이 그대로라는 것은 화면이 어수선해지는 정도가 그대로라는 뜻이다.** 그래서
비는 값을 올리지 않았다 — 올리면 결이 상한 140%를 넘는다(실측: 진하기를 1.2배로
올리자 정확히 140%, 1.4배에서 145%).

눈은 달랐다. 결이 108%로 여유가 많은데 **'약하게'의 평균 밀림이 0.30 으로 바닥(0.3)에
딱 걸렸다.** 진하기를 `0.46/0.60/0.74 → 0.62/0.78/0.94` 로 올려 0.50 / 2.16 / 7.01 이
되었고 결은 113%다.

**`blend` 경로는 통째로 걷어 냈다.** 덧씌우는 효과 셋(비·눈·주변 어둡게)이 전부
알파를 쓰게 되어, 밝기 면만 섞던 옛 길을 쓰는 곳이 하나도 남지 않았다. 안 쓰는
함수를 "이 파일에서 가장 중요한 한 줄"이라는 설명과 함께 남겨 두면 다음 사람을
오도한다. 그 교훈은 `memory/ffmpeg-effect-layer-traps.md` 에 있다.
